## 1. What is wanted

`lexsys-hooks` today is outbound: a client `POST`s an event to `POST /events`, the service stores it, signs it with Standard Webhooks and delivers it to subscribed endpoints (README, `docs/design.md` sections 1 to 4). The wanted addition is the same machine **in reverse**: a public URL per *source* (Stripe, GitHub, Shopify, Slack, or any provider that signs with an HMAC) that

1. **receives** the provider's webhook and answers `2xx` **only after the request is durable** (the flush of `docs/design.md` section 13), so that an acknowledged webhook is never lost, across `kill -9` and power cuts;
2. **verifies** the provider's signature and stores nothing when it does not verify;
3. **stores** the exact raw body, with the headers that matter, in the same log the outbound path uses;
4. **forwards** it, byte for byte, to one or several internal services, with the retries, idempotency, dead letters, history and replay that already exist;
5. is **one more program of the same shape**: same data directory, same single binary, same authority report, no `Ffi`.

**The claim, in one sentence:** *no webhook that was answered `2xx` is lost, the stored bytes are exactly the bytes the provider sent, and the bytes forwarded are exactly the bytes stored.* It does **not** claim that no webhook is ever refused (a provider that gets a non-`2xx` must retry, and one of the four, GitHub, does not: section 3), nor exactly-once delivery, nor ordering.

**Not wanted in this design:** transformations of payloads; pulling missed events from a provider's API (GitHub and Stripe have APIs for that; it is the one thing that would close GitHub's gap and is listed as an open question); answering a provider with content (Slack slash commands and interactivity responses use the HTTP response; a store-and-forward gateway cannot, and only the Events API and the `url_verification` handshake are in scope); horizontal scale; multi-tenant isolation beyond the admin token (`docs/design.md` section 1 says the same of the outbound service); and anything the outbound service is already documented as not being, including **"Not for production"** (README, Limitations): this design inherits every limit listed in section 14 and does not remove them.

**Competitive context** (a search done before this document, re-checked where cheap): Svix Ingest and Hookdeck Event Gateway are managed services that verify provider signatures, fan out and retry ([Svix Ingest](https://docs.svix.com/ingest/receiving-with-ingest), [Hookdeck verification](https://hookdeck.com/docs/use-cases/receive-webhooks/how-to-verify-incoming-webhooks), from search summaries; Hookdeck adds an `x-hookdeck-verified: true` header and signs what it forwards with its own `x-hookdeck-signature`, which is the "re-sign" option of D8 below). Convoy is the self-hosted one that receives ([README](https://github.com/frain-dev/convoy): PostgreSQL required, Redis optional for the queue). **Correction to the premise of the request: Convoy's `LICENSE` on `main` is the Elastic License 2.0, not MIT** (read at [github.com/frain-dev/convoy/blob/main/LICENSE](https://github.com/frain-dev/convoy/blob/main/LICENSE)); that is a source-available licence, not an OSI open-source one, so "the only open-source option that receives" is not established by what I read. It may have been MIT in earlier releases; I did not check the history. What this project would offer is narrower than any of the three and should be sold as that: one static binary, one data directory, an authority report that fits on a screen, EUPL-1.2 (the repository's licence), and a crash-safety argument that is tested with power cuts rather than asserted.

## 2. What the code does today that this builds on (read from the source)

Cited as `file` `function`. Every statement here was read at `1da3c85`, except those marked measured.

### 2.1 Ingest, storage and the flush

* **`handle` (`src/hooks.ls`), route 2, `POST /events`.** It validates the body with `invalid_event` (a JSON object with a string `"type"`, else `422`), reads the `Idempotency-Key` header (`key_header`: one only, `idem.valid`: 1 to 255 visible ASCII), appends a record with `event_record` and `log.append`, sets `note[0]` to the new id, and returns. `run` then **holds** the connection (`server.hold`), and after the turn's last request calls `log.flush(lg)` once; only then does it `server.answer` each held request with `202 {"id":N}`, or `503` if the flush failed. This is the group commit of `docs/design.md` section 13, and the order *flush, then answer* is the property the power-cut mutants of that section pin ("flush after sending the acknowledgements": killed 6 of 6, and worse than loss: acknowledged ids were reused).
* **The record (`event_record`, and `lexsys-log`'s `record.ls`, pinned at `6b4f46f`).** A record is `len(4) crc(4) ms(8) seq(8) fields(4)` and then `fields` pairs, each `u32 length + bytes` twice (name, value); little-endian; `crc` is CRC-32C of everything after it; `len` may not exceed `max_len()` = **65,536** (`log.append` answers `too_long`). The event id is `ms`. An unkeyed event is one pair, `event` = the raw body bytes; a keyed one is three, `event`, `key`, `t` (eight bytes, Unix ms). Bodies are stored verbatim: the JSON check happens before, and the bytes appended are the bytes received. The exact limits fall out of the layout: **a 65,499-byte body is accepted and a 65,500-byte one is refused** unkeyed (measured: 65,499 gives `202`, 65,500 gives `413`), less 28 and the key's length with a key. (README's Limitations says "over 65,500 bytes are refused"; its API table says 65,499. 65,500 itself is refused, so Limitations is off by one; see 2.5.)
* **The pinned `lexsys-log` is one file per log, not segments**: `open_log` opens `events.seg` and `delivery.seg` in the data directory, recovers each to its last whole record (a torn tail is cut), and `log.read_at` reads only below the synced mark, so delivery never sends an event whose `202` has not been given. There is no compaction, retention or index: README says `delivery.seg` is never compacted, `docs/design.md` section 23 says the same of the events log, and `find_event` (`GET /events/:id`) and `find_offset` (replay) are linear scans.
* **`rebuild` (idempotency index at start) treats any record with three or more fields as a keyed event.** It requires the second pair to be named `key` (3 bytes, first byte `k`) and the third `t` with an 8-byte value, and otherwise **returns 16 and the service refuses to start**. So the record shape of section 5.3 below cannot be written until `rebuild` finds its pairs by name. This is the first piece of work, and it also means a log containing inbound records cannot be read by the current binary (it would refuse at start, nothing lost: the same trade 25.1 made for the slot records).

### 2.2 Idempotency (`src/idem.ls`, `handle`)

An open-addressing table of **65,536 keys** (`idem.capacity()`), keys 1 to 255 visible ASCII bytes, an arena of `65536 * 255` bytes, a window (default one day, `--window-ms`) measured from the time in the record. A repeat with the same key and the same body (CRC-32C and length) is answered with the first event's id **after the turn's flush**; **the same key with another body is `422`**; a key not held when 65,536 are held is **`507`** ("the index refuses, it never forgets", section 17). An expired key is never removed; only the same key arriving again overwrites its entry. Read from `handle`: the `507` test is `entry < 0 && idem.count(ix) >= idem.capacity()`, so **once 65,536 distinct keys have been seen, every event with a new key is refused, whether or not the old ones have expired.** That is right for an API whose client can retry and wrong for a public webhook endpoint (D9).

### 2.3 The HTTP server (`http-server` pinned in `lex-sys.toml`, `std.http`) and what the loop does

* `server.open(heap, p, listener, max_len() + 4096, 0, 9)`: each connection has an input buffer of **69,632 bytes** (head and body together), at most 1,024 connections (the 256 MiB input budget divided by the buffer size, capped at 1,024), idle connections closed after **9 seconds** without progress. One listener, one thread, one poller.
* A request that cannot fit is answered **`413 request too large`** and the connection is closed. **Measured** with a raw socket and a declared `Content-Length`: 65,500 bytes, 69,632, 150,000, 1,000,000 all got `HTTP/1.1 413 Content Too Large`; at 5,000,000 bytes the client's `sendall` failed with a reset (the server had answered and closed while the client was still writing) but the `413` was readable on the socket. A 100,000-byte chunked body got `413` too. `docs/design.md` section 17 says the opposite ("answered by closing the connection, not with 413: the client sees a reset"); see 2.5.
* **At most 64 headers** including `Host` and `Content-Length` (`http.slots(64)`): measured, a request with 62 extra headers is served, 63 or more is `400 too many headers`. A reverse proxy adds some (`X-Forwarded-For`, `X-Real-IP`, ...), so a provider that sends more than about 55 is refused. None of the four documented header sets comes near this.
* Chunked request bodies are decoded by the server before the handler sees them (`http.dechunk`); the handler's `body` is the decoded bytes, which is what a provider signed. A header value cannot contain CR, LF or other controls (`std.http`'s header-value character class), so a stored header cannot smuggle a second header when it is forwarded.
* **Nothing is authenticated except the endpoint-management routes.** `manage.authorize` (bearer token, constant-time over 255 positions) guards `POST /endpoints` and `PATCH /endpoints/:id` only. `GET /events/:id` returns the stored event to anybody who can reach the port; `/stats`, `/config`, `/endpoints`, `POST /events` and `POST /events/:id/replay` likewise (design 25.2: "The token is the only barrier" for management; the rest is open by decision). **That is fine for an internal service and disqualifying for a public one** (D2).
* The loop is one thread: `handle`, the flush, `delivery_turn`, the history pool. **Measured: an HMAC-SHA256 of a 65,000-byte body with `src/sign.ls` costs about 1.2 ms** (about 0.25 ms at 1,000 bytes, 0.54 ms at 16,000; `build/sign_probe` run 20 times per size, the 1.21 ms process start subtracted; the result was equal to Python's `hmac` each time). That is roughly **800 maximum-size verifications a second** on the one core that also serves ingest and delivery, which is the number every abuse decision below is judged against (D14).

### 2.4 Delivery (`start_attempts`, `start_one`, `request_for`, `finish_attempt`, `src/state.ls`, `src/attempt.ls`)

* **State is a cursor and a window of 1,024 cells per endpoint slot** (`state.span()`, `state.max_endpoints()` = 62), keyed by the dense event id; events above `cur + 1,024` are not considered. Up to **8 attempts in flight per endpoint** (`per_endpoint()`), 16 started a turn (`most_starts()`), 64 in flight in all, a 2,000 ms default deadline for connect, send and the status line (`default_deadline_ms()`).
* **`request_for` fixes everything about the request except the body and the signature:** `POST /hook HTTP/1.1`, `Host: receiver`, `Content-Type: application/json`, `webhook-id: evt_<id>`, `webhook-timestamp` (Unix seconds, **taken when the attempt starts**), `webhook-signature` (`v1,` + base64 HMAC-SHA256 of `id.timestamp.body` under the endpoint's decoded secret), `Content-Length`, `Connection: close`. The body is the first pair of the record, read at the offset in the window's `offs` table. There is no per-endpoint path, no per-endpoint `Host`, and nothing from the stored request is forwarded.
* **The request buffer is 66,560 bytes per attempt slot** (`attempt.req_max()`, 64 slots: 4.26 MB). A request that does not fit is `no_send` (a failed attempt). Today's largest body, 65,499, plus about 384 bytes of headers fits; a body that is large *and* carries stored headers would not.
* **Any `2xx` delivers; `410` is a dead letter and disables the endpoint; anything else retries** on the Standard Webhooks schedule (5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 14 h, 20 h, 24 h, then dead) and **a retry re-signs with a fresh timestamp** (the timestamp is read in `start_one`/`start_replay` per attempt). The outcomes go to `delivery.seg` (77 bytes a record: `state.put_outcome`, 28 + 4 + 1 + 4 + 40), the history row to `attempts` best effort.
* **A stuck cursor stalls everybody after 1,024 events.** `extend_scan` reads the events log only up to `lowmark(dv) + state.span()`, where `lowmark` is the **slowest cursor of all endpoints in the table** (disabled ones included). Section 25.2 measured this for a row added by hand (A "is sent none of the next ten events"); the same arithmetic applies to any endpoint whose cursor stops, for example a poison event that its receiver answers `400` to for the 75-hour life of the schedule (5 s + 5 m + 30 m + 2 h + 5 h + 10 h + 14 h + 20 h + 24 h): the endpoint is served for 1,024 more events and then not at all, **and because the scan is bounded by it, neither is any other endpoint**. At one event a second that is 17 minutes; at 100 a second it is about ten seconds. *I derived this from `extend_scan` and `lowmark` and from section 25.2's measurement; I did not re-measure it for a stuck cursor.* It is the largest engineering risk in this design (D18), because a gateway sees poison events as a matter of course and the outbound service, whose client is the sender, mostly does not.
* **Replay (`POST /events/:id/replay[/:endpoint]`)** re-sends a stored event to one or all endpoints with the same `webhook-id` and a fresh timestamp, through the same attempt machinery (section 23). Capacity 32 waiting.
* **`attempts` (PostgreSQL)** is keyed `(endpoint, event, replay, attempt)` and is by event id, so it works unchanged for inbound events. **`endpoints`** has `id, host, port, secret`; the secret is `whsec_` + base64 and **is stored in the clear** because the service must sign with it (24.1). `POST/PATCH /endpoints` take effect without a restart: the database first, memory only on commit, one change at a time in the `mg` block (368 integers), `409` while another waits (25.2 to 25.4).
* **Destinations must be public IPv4 literals** unless `--allow-private-hosts 1` (`src/destination.ls`, section 26): no names, no private, loopback or link-local ranges. **Forwarding to internal services is exactly what that policy refuses.** The only existing switch is the boolean, which turns the whole policy off (D17).
* **No outbound TLS** (README: "no `https`"; design section 9). Forwarding to an internal service is plaintext HTTP.

### 2.5 Statements in the existing documents that this found false

* **`docs/design.md` section 17, "Found along the way", second bullet:** *"A request over the server's input limit (about 69.6 KB) is answered by closing the connection, not with `413`: the client sees a reset. That is `http-server`'s behaviour."* **False for the `http-server` pinned in `lex-sys.toml` now** (`f804ce7`; whatever the pin was when section 17 was written): `produce` refuses a request whose head plus declared length exceeds the buffer with `413` and the message `request too large`, and the probes of 2.3 got that `413` at every size from 65,500 bytes to 1,000,000, with the reset appearing only for a client still writing megabytes. The practical effect for a provider is the reverse of what the sentence says: it gets a `413` it can log.
* **README, Limitations:** *"Events over 65,500 bytes are refused (`413`)."* A 65,500-byte body is refused; the limit is 65,499 (the README's own API table says "over 65,499 bytes").
* **Where the corrections belong.** Both statements are in files I was told not to edit (README, and `docs/design.md` except for one appended paragraph), so **I have not corrected them in place**; the parent session should make those two edits (a sentence in section 17, a number in the README). They are written down here so that they are not lost.

| **Generic** | whatever the provider does | unknown | n/a |

**What follows for the gateway.**

1. Answering after the flush is inside every budget above: the flush is one `fsync` shared by the turn (`docs/design.md` section 16 measured ingest at a 2.3 ms median and about 80 ms p99 with delivery running). The budget that could be broken is Slack's 3 s by a disk that stalls for seconds; that is a gate (S1), not an assumption.
2. **An answer that is not `2xx` is a loss for GitHub and a retry for the others.** So the gateway's own availability matters most for GitHub, and "never lose a webhook" is true only for the ones the gateway acknowledged. State this next to every promise (README, the `/in` documentation).
3. **`503` means "try again" and must be used for every condition that is the gateway's fault** (log broken, disk full, a verification budget spent); **`401` means "this will not work" and must be used for every condition that is the sender's** (bad signature, stale timestamp). Stripe retries a `401` for up to three days and a Slack app that fails more than 95% is disabled: a wrong secret is loud by design.
4. **`url_verification` (Slack):** when an app's Request URL is set, Slack sends `{"type":"url_verification","challenge":...}` and expects `HTTP 200` with the challenge value back (V2). Whether that request is signed: **NV**. The gateway answers it itself (D5) and stores nothing.

## 4. Decisions

Each has what it is, the alternatives, and why. **to confirm** marks what changes behaviour a person may rely on.

### D1. Reuse `events.seg` and the delivery engine; extend the record, add no second log. (to confirm: a log with inbound records cannot be read by the current binary)

**Alternatives.** (a) A separate `inbound.seg` for raw receipts, and a copy into `events.seg` when forwarded. Rejected: that is two durable stores and a crash between them, the failure `docs/design.md` section 3 exists to prevent (one source of truth per fact). (b) One log per source. Rejected: the cursor, window, `offs`, replay, history and idempotency index are all keyed on **one** dense id sequence; one log per source multiplies every one of them. (c) Reuse the log and **encode** the source and headers inside the body. Rejected: it breaks "the stored bytes are the provider's bytes" and every reader of the first pair.

**Chosen.** The same `events.seg`; the first pair stays `event` = the raw body, so `start_one`, `start_replay`, `find_event` and every harness that reads the first pair keep working; the new facts are further named pairs (section 5.3). Prerequisites: `rebuild` must find `key` and `t` by name (2.1); `GET /events/:id` must not print a non-JSON body as a JSON fragment (`find_event` puts the first pair into a JSON object with `put_fragment`; for a form-encoded Slack body that is invalid JSON). The cost: **a log with an inbound record is refused at start by the previous binary** (it returns 16, nothing is lost), so the upgrade is one-way once a source exists.

### D2. The only public route is `POST /in/:token`; with `inbound 1`, every other route needs the admin token. (to confirm)

**The problem.** A public webhook URL must be reachable from the internet, and the service today answers `GET /events/:id` (the stored bodies, possibly with customer data), `/stats`, `/config`, replay and `POST /events` to whoever can reach the port (2.3). Putting the gateway on the internet through a reverse proxy that forwards only `/in/*` works, but it is a deployment rule the service does not enforce, and "refuse, don't downgrade" is the discipline of this repository.

**Alternatives.** (a) Rely on the proxy. Rejected as the only defence. (b) A second listener (an internal admin port). Cleanest, but `http-server` takes **one** `Listener` (`server.open(heap, p, listener, ...)`), so it is a change to lex-sys, not to this project. (c) A new setting `inbound = 1` that makes the service **refuse to start without an `admin-token`** and then requires the bearer token (`manage.authorize`, already constant-time) on every route except `POST /in/:token` and `GET /healthz`. Existing clients of the open routes would then need the token, which is why it is behind a setting and off by default.

**Chosen: (c); (b) remains the better end state** and is listed in the open questions. `GET /stats`, `/metrics` and `/config` are behind the token too.

### D3. A source is addressed by a random token in the path; the HMAC is the authority.

**Alternatives.** (a) The numeric source id in the path (`/in/17`). Guessable, so an attacker can aim bad requests at a known source and make the service spend HMAC time on it. (b) **The URL as the only secret** (some providers authenticate this way). Rejected: URLs end up in proxy and provider logs; for the four providers here there is a real signature, and the URL must not be what a leak forges. (c) A token **and** the HMAC (chosen): `/in/<token>` with at least 128 bits of random from `/dev/urandom` (`manage.make_secret` already reads it), constant-time compared over the (at most 64) sources; an unknown token is `404` **before any cryptography**, so the unauthenticated cost of a guess is a lookup. The token is an identifier, not a secret: it is shown by `GET /sources` to the admin, and nothing is authorised by knowing it.

### D4. Verification before storage, one scheme per source kind; a failure stores nothing and logs a counter, never the body.

Kinds: `github`, `stripe`, `shopify`, `slack`, `hmac` (generic). Each is a pure function from (the stored secrets, the request's header values, the raw body, now) to *verified*, *bad signature*, *stale*, or *malformed*, with no effect, so it is testable from bytes like `sign.ls`:

* `github`: `X-Hub-Signature-256` is `sha256=` + 64 hex digits; MAC the body under the secret's bytes (the secret text itself, not base64-decoded).
* `stripe`: parse `t=` and every `v1=`; reject if `abs(now - t) > tolerance` (default 300 s, the libraries' default, V1) **before computing anything**; MAC `t + "." + body`; accept if any `v1` matches; ignore `v0` and unknown keys. **What the key is is not settled by what I read:** I believe Stripe uses the `whsec_...` string itself as the HMAC key (unlike Standard Webhooks, whose key is the base64-decoded secret, `sign.secret_key`), but I read `_webhook.py`'s header parsing and comparison and not its key handling, so this is a belief. The S2 gate settles it by generating the header with `stripe-python` and requiring the gateway to accept it.
* `shopify`: `X-Shopify-Hmac-Sha256` is base64 of the 32-byte MAC of the body (`sign.b64_decode` exists and is strict).
* `slack`: `X-Slack-Request-Timestamp` and `X-Slack-Signature` (`v0=` + hex); reject if `abs(now - ts) > 300` before the MAC; MAC `"v0:" + ts + ":" + body`.
* `hmac`: configured header, algorithm SHA-256 only, encoding `hex` or `base64`, optional fixed prefix, signed content `body` or `<timestamp>.<body>` with a configured timestamp header and tolerance. No other templating: a general template language is how a verifier gets a hole.

**The comparison is a new constant-time byte compare over decoded MACs (32 bytes each)**, not a text compare: `sign.ls` has base64 but **no hex decoder and no MAC compare** (the only constant-time code is `manage.authorize`'s, specific to the token), so both are new. Hex is decoded strictly (exact length, both cases accepted, nothing else).

**Alternatives.** (a) Compare the hex *text* with a constant-time text compare: that makes the comparison depend on the case and on the encoding the sender chose; decode both, compare bytes. (b) Verify after storing, discard on failure: rejected, an unauthenticated request must not cost a flush. (c) A signature scheme per provider chosen at run time from the header present ("auto"): rejected, an attacker chooses which weaker scheme is tried.

**On a failure:** `401` (`bad signature`, `stale timestamp`, `missing signature`) or `400` (a header that is not the shape: not 64 hex digits, no `t=`), **nothing appended, nothing flushed**; a per-source counter by reason is incremented; the log line (stderr, as today) names the source id and the reason, **never the body, never a header value, never the signature**.

### D5. The acknowledgement is `200`, after the flush; Slack's challenge is answered by the gateway.

The `2xx` is `200 {"id":N}`, **not `202`**: all four providers document "2xx" (GitHub, Slack: V1/V2; Shopify's text says 200 OK in the secondary sources), but a sender that tests `== 200` is the failure that costs a webhook, and `std.http` has no reason phrase for `202` (measured: `HTTP/1.1 202 Unknown`). The body is ignored by every provider here. For a `slack` source whose verified body is `{"type":"url_verification",...}`, the answer is `200` with the `challenge` value as the body, nothing is stored, and a counter says so (`json.get` over the body, the same call `invalid_event` uses). The answer is given only for a **verified** request: whether Slack signs the handshake is NV, so if it does not, setup would fail with a `401` and the fix is a one-line change guarded by a test (open question 9).

### D6. The raw body is stored as received; no JSON check; `Content-Encoding` is refused.

`invalid_event` (a JSON object with a string `type`) is **not** applied: a Slack interaction is form-encoded, a GitHub webhook may be, and a generic provider may send anything, and a body the gateway rejects because it is not JSON is a webhook lost. The bytes appended are `server.body(sr)`: for a chunked request that is the decoded body, which is what the provider signed. **A request with a `Content-Encoding` other than identity is refused `415`** before verification, because a signature over bytes the gateway cannot interpret is not worth storing; none of the four is known to send one (3.3), and a loud `415` beats storing bytes under a signature that might have covered the decoded form. (**to confirm**: it is a refusal of a request that could have been stored.)

### D7. Headers: an allow-list is stored as received and forwarded as received; hop-by-hop and credentials are never stored.

**What is stored** (the `hdr` pair): the allow-listed headers of the request as `Name: value` lines in arrival order, the value exact (OWS around it trimmed by the parser, which is the only normalisation), capped at **4,096 bytes** in all, signature and id headers first. The allow-list per kind: `github`: `X-GitHub-*`, `X-Hub-Signature`, `X-Hub-Signature-256`, `User-Agent`, `Content-Type`; `stripe`: `Stripe-Signature`, `Content-Type`, `User-Agent`; `shopify`: `X-Shopify-*`, `Content-Type`; `slack`: `X-Slack-*`, `Content-Type`; `hmac`: the configured signature and timestamp headers, `Content-Type`, `User-Agent`, plus up to eight configured names. **Never stored or forwarded:** `Authorization`, `Cookie`, `Proxy-*`, `X-Forwarded-*`, `X-Real-IP`, `Forwarded`, `Host`, `Content-Length`, and the hop-by-hop set of RFC 9110 (`Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`, and any header named in `Connection`).

**Alternatives.** (a) Store every header: the record is limited to 65,536 bytes **including** the headers (`len`), the head can be 64 headers of arbitrary size, and a stored `Authorization` or `Cookie` (a reverse proxy may add one) is a secret in a log that has no retention. (b) Store nothing but the signature headers: loses `X-GitHub-Event` and the rest the receiver routes on. **(c) allow-list (chosen):** the receiver sees what it would have seen from the provider, and the record's size is bounded. Overflow of the 4,096 bytes drops the later headers and increments a counter; the body is never touched.

**Forwarded request.** `POST <path> HTTP/1.1`, `Host: <host header>`, the stored lines, the Standard Webhooks triple (D8), `Content-Length`, `Connection: close`, then the body. `<path>` and `<host header>` become **per-endpoint** fields (`endpoints.path`, default `/hook`; `host_header`, default what `request_for` sends today, `receiver`). `Content-Type` is the **stored** one, not the fixed `application/json` of `request_for`; an event stored by `POST /events` has none stored and keeps `application/json`.

### D8. Forwarding carries both signatures by default: the provider's, passed through, and Standard Webhooks, fresh per attempt. (to confirm)

**The tradeoff, stated plainly.**

* **Pass the provider's signature through (`signing = provider`).** The receiver verifies it exactly as it would with the provider directly, so an existing internal service needs no change, and nothing it trusts is the gateway. **But Stripe's `t=` and Slack's timestamp are the original ones and the libraries reject anything older than 5 minutes (V1)**: attempt 1 passes, the retry after 5 s passes, the retry after 5 minutes does not, and **every replay fails**. Stripe solves this by re-signing each retry; a pass-through gateway cannot without the secret. (GitHub and Shopify carry no timestamp, so their signatures verify forever.)
* **Re-sign with our own Standard Webhooks signature only (`signing = standard`).** One scheme for every provider; a fresh timestamp each attempt (already what `request_for` does), so retries and replays verify; a receiver that already speaks Standard Webhooks (this service's own receivers) needs nothing new. The provider's signature headers are removed. The cost: the receiver trusts the gateway, not the provider (it cannot check the provider's signature), and every internal receiver must be changed to verify a second scheme, which for a stack that today verifies Stripe's signature is real work.
* **Both (`signing = both`, the default):** the stored provider headers pass through unchanged **and** the Standard Webhooks triple is added. A receiver chooses what to verify; **it must be told which to choose per provider**: for `stripe`, `slack` and any `hmac` source with a timestamp, verify Standard Webhooks (the provider signature is informational after five minutes); for `github` and `shopify` either.
* **Re-sign in the provider's format with a fresh timestamp** (what Stripe does itself): possible because the gateway holds the secret. Rejected: it is forging the provider's signature, the receiver can no longer tell a provider-signed request from a gateway-signed one, and the gateway then has to emit four signature formats.

**Chosen: `both`**, with `provider` and `standard` selectable per route (D10). `webhook-id` is `evt_<id>` as today (stable across attempts and replays); an added `X-Hooks-Source: <source name>` says where it came from.

### D9. Deduplication is per provider, keyed by the provider's own id, namespaced by source; a repeat is a `200`, never a `422`; a full index never refuses an event. (to confirm)

| source | key | where read | level |
|---|---|---|---|
| `github` | `X-GitHub-Delivery` (a GUID; **a manual redelivery keeps it**) | header | V1 |
| `stripe` | the event's top-level `"id"` (`evt_...`) | body, `json.get` | NV in this session (the docs page was not readable); it is the id of the event object |
| `shopify` | `X-Shopify-Webhook-Id` | header | the sources name both it and `X-Shopify-Event-Id`: **NV which is right**, to be settled from shopify.dev's "ignore duplicates" page before S4 |
| `slack` | the payload's `"event_id"` (globally unique; V2); interactions and slash commands have none, so no dedupe | body | V2 |
| `hmac` | an optional configured header; none by default | header | n/a |

The index key is `<source id>:<provider key>` (at most 255 bytes; a provider id longer than that is hashed, SHA-256 and hex, and the cap says so), so two sources cannot collide and a source can be deleted without touching another's keys. The existing `idem` index and `key` pair carry it unchanged.

**Three departures from the outbound API's rules**, each because the client is no longer in control:

1. **The same key with different bytes is `200`, not `422`.** Outbound, a client reusing a key for a different event is a bug worth a `422`. Inbound, the provider chose the id and retries it; if the bytes differ (Stripe's `pending_webhooks` may, NV), a `422` makes the provider retry for days. The duplicate is acknowledged after the original's flush, nothing is stored, and a counter `dedupe_conflict` (a different CRC under the same key) is incremented so that a person can look.
2. **A full index never refuses.** Outbound the index answers `507` (2.2) because the client can retry; inbound a `507` is a lost webhook (GitHub does not retry). When 65,536 keys are held and one is new, the event is **stored without a key** and `dedupe_skipped` is incremented: a possible duplicate (which delivery tolerates: at least once) over a certain loss. The real fix is that **expired entries must be reclaimable** (a key older than the window is dead weight; at 65,536 keys and a one-day window the index fills at 0.76 distinct events a second, which a busy Shopify store exceeds in an afternoon). That is S0.
3. **Dedupe can be turned off per source** (`dedupe = 0`). **Why it matters for GitHub:** GitHub does not retry, so a repeated delivery id means a *person pressed Redeliver*, who wants it processed; with dedupe on and inside the window, that press is acknowledged and swallowed. Against that, **replay protection**: GitHub and Shopify carry no timestamp (3.1), so a captured valid request replays forever unless the delivery id is remembered, and the window bounds that. **Default: on for every source**, with this paragraph as its documentation; a GitHub operator who wants manual redelivery switches it off and uses `POST /events/:id/replay` instead.

### D10. Fan-out is a pure function of the route table and the record; non-matching events cost nothing in the log. (to confirm)

**What is wanted.** One source, several destinations, each with its own filter. The existing engine delivers **every event to every endpoint** (a cursor over the whole log). For a gateway an endpoint wants only the events of the sources routed to it, and perhaps only some types.

**Alternatives.** (a) **A "skipped" outcome record per non-matching (endpoint, event).** Simple and obviously recoverable, but `delivery.seg` is never compacted and a record is 77 bytes: ten destinations at 100 events a second is 77 x 10 x 100 x 86,400, about **6.7 GB a day of records that say nothing**. (b) One log per source (D1). Rejected. (c) **A pure `wanted(slot, event)`**: an event is wanted by an endpoint if a route `(source, endpoint)` exists, the event's id is above the route's `since_event`, and the event's type passes the route's filter; each of those is in memory (the route table) or in the event's own record. A non-wanted event is final for that endpoint **in memory** and advances the cursor in memory; at a restart the scan simply decides it again.

**Chosen (c)**, with three rules that make it correct:

1. **A route starts from now.** `since_event` is the last event id when the route is created (the rule D2 of section 25 gave `POST /endpoints`, for the reason 25.2 measured). A route is never backdated.
2. **Routes are immutable except `enabled`**; changing a filter is delete and create, which gets a new `since_event`. Otherwise an edit would change the answer of `wanted` for events already in the window, and a pending event would be dropped or sent depending on whether the process had restarted.
3. **A sparse `advance` record** (a new outcome kind: endpoint slot, up-to id) is written when the in-memory cursor has moved over skipped events by at least 256 ids or 5 seconds, so a restart does not re-walk a long run of events nobody wants. It is an optimisation of restart time, **not** a correctness requirement, because `wanted` is pure; a lost `advance` costs a re-scan of at most the unrecorded run. It asserts only "everything up to here is final or not wanted", so replay applies it with `max`.

The scan reads each record once (`extend_scan` already does); it would cache `source` and a hash of `typ` in a per-window `meta` array, 1,024 x 2 integers beside `offs`, so `wanted` is an integer test. **Risks:** this changes `start_attempts`, `lowmark` and `state.apply`, the most tested and most delicate code in the repository (section 25 found an overlapping-offsets bug there); it interacts with D18 (below); and "a route is deleted while its events are pending" **drops them**, which is what delete means and which the API must say (D16).

### D11. Event types for filters: read cheaply or not at all. Stored in the record.

A filter is a list of exact type names (`push`, `invoice.paid`, `orders/create`); no patterns in the first version. **Cheap** means from a header, no body parse: `github` `X-GitHub-Event`, `shopify` `X-Shopify-Topic`, and a configured header for `hmac`. **Not cheap:** `stripe` (`"type"` in the body, a JSON parse of up to 64 KB, the cost `invalid_event` already pays on every outbound event, unmeasured here) and `slack` (`event.type` for an `event_callback`, nested, with `type` at the top for the handshake and for interactions). Both are done in the same pass that extracts the dedupe key (D9), so the body is parsed once, at ingest, only for sources that have a filter or a dedupe key in the body. The type is stored in the record (`typ`, at most 128 bytes; longer or absent is stored empty and passes only the "all types" route), so `wanted` never parses a body.

### D12. Ordering: what is NOT guaranteed.

Say it plainly, in the README and in the `/in` documentation:

* **No ordering between sources, and none the providers promise** (GitHub, Shopify, Slack, Stripe do not document delivery order in what I read; NV for Stripe).
* **Arrival order is flush order**: ids are assigned in the order requests are handled within a turn, which is not the provider's send order.
* **Attempts start in id order at a healthy endpoint, but up to 8 are in flight per endpoint** (`per_endpoint()`), so the receiver can see N+1 finish before N.
* **After any failure the retry of N and the first attempt of N+1 are not ordered** (`docs/design.md` section 4, deliberately).
* **A replay is out of order by definition.**
* **Exactly once is not offered.** At least once, with `webhook-id` (`evt_<id>`) for the receiver's own dedupe; a crash between a `2xx` from the receiver and the outcome record's flush repeats an attempt (`docs/design.md` section 14 measured 9 such repeats in 393 requests under 101 kills).
* A receiver that needs order sorts on the provider's own sequence fields (a Stripe `created`, a GitHub delivery's `X-GitHub-Delivery` is *not* one) or uses the provider's API as the truth.

### D13. The body limit stays at the record limit (65,536); raise it only on evidence. (to confirm)

**What the current limit means per provider.** The largest accepted body is **65,499 bytes unkeyed** (2.1); an inbound record also carries the headers (up to 4,096), `src`, `key`, `typ` and `t`, so the guaranteed ceiling is about **61,000 bytes** with every cap hit and about **64,700** with ordinary headers (arithmetic from the layout in 5.3). A bigger body is `413`. GitHub states a **25 MB** cap, so a large `push` or `create` can exceed ours (V1); Shopify, Stripe and Slack publish no cap I could read (NV), and an order, an invoice with many lines or a product with many variants can be tens of kilobytes. What a refusal costs: `413` is non-`2xx`, so Stripe, Shopify and Slack retry the same bytes (and get the same `413`) and GitHub loses it; a Slack app failing 95% is disabled. **A `413` here is a loud loss, and it needs a counter and an alert (D19), not silence.**

**What raising it costs in the fixed-size design (read, and arithmetic from it):**

| what is sized by the limit `L` | now (65,536) | at `L` = 1 MiB | at `L` = 25 MiB |
|---|---|---|---|
| request buffers for attempts: `attempt.req_size()` = 64 x (`L` + about 1,024) | 4.26 MB | about 67 MB | about 1.7 GB |
| the server's input buffer per connection (`L` + 4,096), and the connections that fit in its fixed 256 MiB budget (`connection_limit`) | 69,632 B, 1,024 connections (the cap) | about 1.05 MB, **about 255** connections | about 25 MiB, **about 10** connections |
| the record scratch (`scratch`, `L` + 8,192) and the log window (`L` + 4) | 73 KB | 1 MiB each | 25 MiB each |
| one HMAC on the single thread (measured, 1.2 ms per 65 KB) | 1.2 ms | about 18 ms | about 460 ms |
| a group-commit `fsync` of the turn's bytes | small | up to megabytes per turn | |

And two limits that are not arithmetic: **a region's arena is 64 KiB** (`docs/design.md` section 13: scratch above that is a heap box), and `record.len` is a 32-bit field but `max_len()` is a constant the log is recovered with, so raising it is a change to what recovery accepts (a log written with a higher limit is refused by a binary with a lower one). **Conclusion:** keep 65,536 for the first slices, count `413`s per source and kind, raise to 256 KiB only when a source's counter shows traffic that matters (the cost at 256 KiB is about 17 MB of attempt buffers, about 1,000 connections, 4.6 ms an HMAC, all fixed at start), and treat GitHub's 25 MB as out of reach for this design without a **spill** (the body in a side file named by its hash, the record holding the hash and length; a separate design with its own crash argument: the body file is flushed before the record that names it). Not in these slices.

### D14. Abuse and rate limits: cheap checks first, per-source buckets, a global verification budget. (to confirm the numbers)

An unauthenticated public endpoint on one thread. **The cost to defend is the HMAC (about 1.2 ms for a maximum-size body, measured), the flush for a valid request, and the connections.** Layers, in the order a request meets them:

1. **The reverse proxy** (section 11): TLS, request buffering (it reads the whole request before the service sees a byte, which removes slow-body attacks on a service whose connection cap is 1,024), a body limit equal to the service's, and a connection and rate limit per client address, which is where an IP-based limit belongs because the service sees only the proxy.
2. **Unknown token: `404`, nothing computed** (D3).
3. **A per-source token bucket** (in memory, lost at a restart: a fact that "can be lost without harm", `docs/design.md` section 3) applied **before the HMAC**: a rate (default 50 a second) and a burst (default 200) per source, `429` with `Retry-After: 1`. It also bounds the flush rate a single source can force. A *verified* request over the limit is rejected too, which loses it for GitHub: so the defaults are generous, the counter is per source, and the limit can be set to 0 (off). **The sender's retry is the backpressure for the other three.**
4. **Cheap structural rejects before the HMAC**: missing signature header, a hex or base64 value of the wrong length, `Content-Encoding`, and for `stripe`, `slack` and timestamped `hmac` a **stale or future timestamp** (more than the tolerance away), so a replayed old request costs no cryptography.
5. **A global verification budget per turn** (like `most_starts()`): at most N bytes of HMAC input a turn (default 4 MB, about 70 ms at the measured rate), beyond which the request is answered `503` with `Retry-After: 1` without verification, so a flood of maximum-size bad requests cannot starve delivery and ingest of the other sources. `503`, not `401`, because it is the gateway's condition.
6. **After failures:** a per-source counter of bad signatures; above a threshold in a window (default 20 a second) the source's *unauthenticated* requests are answered `401` without computing, for as long as the rate stays high. This keeps the cost of a flood at a lookup. It also lets a real provider with a wrong secret be starved of nothing it was not already failing.

**Replay protection.** Timestamped schemes: the tolerance (300 s default, the libraries' default; configurable per source, **never 0**: a source cannot turn the check off, only widen it, up to 3,600 s). Untimestamped (GitHub, Shopify, most generic): **only the dedupe window** (D9): a captured request can be replayed after the window. **Say so.** A defence in depth the service does not build: GitHub documents the `GET /meta` address list (V1); an allow-list at the proxy is the place.

**Constant-time compare.** For MACs (D4) and the token (D3). A functional test cannot kill a mutant that exits early (the answer is the same), so the gate is structural: one function, a fixed loop over the full length, no early return, reviewed, and a unit test that the result does not depend on where the first difference is. This is a limit of the method, stated rather than hidden.

### D15. TLS: a reverse proxy terminates it; the service never sees https.

Providers deliver to `https` URLs (GitHub verifies certificates by default, V1; the others: 3.3). **lex-sys has no TLS** (design section 9 predicted it; README: "no `https`"), so a reverse proxy (nginx, Caddy, a cloud load balancer) terminates TLS and proxies plaintext to `hooks` on a private address. That has consequences to write down in the operator documentation: the service sees the proxy's address, never the sender's (so no IP rules in the service; `X-Forwarded-For` is dropped, D7, and not trusted); the proxy must not rewrite the body (a gzip or charset filter would break every signature: **verification runs on the bytes the service receives, which must be the bytes the provider sent**; the S2 gate runs through a real proxy to prove it); the proxy's added headers count against the 64; and **the internal hop is plaintext** both ways (the provider's payload, possibly with customer data, crosses the internal network to the service and from the service to the receiver). The Standard Webhooks signature protects integrity, not secrecy. A sidecar TLS proxy for outbound is the workaround until lex-sys has TLS; it is not in this design.

### D16. Managing sources and routes: the admin token and the `mg` block, a table each, and no way to lose a stored event by deleting. (to confirm)

* **Routes:** `POST /sources`, `GET /sources`, `GET /sources/:id`, `PATCH /sources/:id`, `DELETE /sources/:id`; `POST /routes`, `GET /routes`, `DELETE /routes/:id`, `POST /routes/:id/enable`, `/disable`.
* **Authority:** the **same admin token** and `manage.authorize` as `POST /endpoints` (D7 of section 25), `403` without one configured, `401` for a wrong one. Alternative: a separate `sources-token`, since a source secret lets whoever holds it forge provider events *into* the gateway where an endpoint's address lets them aim deliveries *out*. Rejected for the first version: one token, one more place to look, and the same stored-secret exposure (below). Listed as an open question.
* **Mechanism:** the `mg` block already carries "the one change that waits for the database" with a kind (`create`, `patch`) and answers `409` while another waits (25.2 to 25.4). It grows kinds for source create, patch and delete and route create and delete; the order is unchanged (D3 of section 25: the transaction first, memory only on commit, a `504` does not assume failure, **no second recovery path**: the next start reads the tables). The block is 368 integers, a byte to an integer; sources carry longer text (a 255-byte secret, a header name, a prefix), so it grows, or a second block is made (S6 decides; the cost is memory only).
* **The secret** of a source is **stored in the clear in `sources.secret`**, exactly as `endpoints.secret` is and for the same reason (the service must compute the HMAC; a hash cannot). It is returned **once**, on `POST /sources` when the service generated it (the GitHub case, where the operator pastes *our* secret into GitHub's form) or echoed from the request, and **never by any read**. Anyone who can read the table can forge provider events into the gateway; the schema file says so, and the database role the service uses should be granted `select` on `sources` and nothing else it does not need. No encryption at rest: lex-sys has no AES (`docs/crypto.md`: SHA-256 only when it was written; the std has since gained SHA-512, not a cipher), and a key in the settings file next to the database credentials would add little.
* **Secret rotation without a gap:** `PATCH /sources/:id {"secret":..., "keep_previous_s": 86400}` stores `prev_secret` and `prev_until_ms`; verification tries the current secret and then, until the time, the previous one (Stripe's roll overlaps up to 24 hours, V2; the time and cost: a second HMAC only for requests that fail the first, bounded by the budget of D14). This is the inbound analogue of the two-signature rotation that section 25 deferred, and it is **cheaper than the outbound one** because verification can simply try two.
* **DELETE** a source: **stops accepting** (`410 Gone` to the provider, so a provider that disables on failure does) **and does not touch stored events or routes**: events already in the window are still delivered (the routes stay until deleted). Deleting a *route* drops its pending events (D10), and the API says "N events are pending for it" in the answer's body and requires `?drop=1` when N > 0. **Pause** (`status = paused`) answers `503` + `Retry-After` and keeps everything.
* **Without PostgreSQL:** a `sources.conf` and a `routes.conf` in the data directory, one line each, read at start, exactly as `endpoints.conf` is (C3). This is how S1 to S5 are built and tested **with no database**; the tables and the management routes are S6. (Same discipline as section 24: the file was the first stand-in, the table the second.)

### D17. Destinations are internal: `allow-cidrs`, not `allow-private-hosts 1`. (to confirm)

Section 26 refuses private, loopback and link-local destinations and names, by default, and offers one switch, `allow-private-hosts`, that turns the whole policy off. A gateway **only** forwards to internal services, so it would run with the switch on, and then a stolen admin token can point deliveries at `169.254.169.254` or any internal admin port, with the response ignored but the action done (section 26's risk, unchanged). **Alternatives:** (a) the boolean (works, weakest); (b) **a list of allowed networks**, `allow-cidrs = 10.20.0.0/16,192.168.5.0/24`: a destination must be an IPv4 literal inside one of them, **and the 169.254.0.0/16 and 127.0.0.0/8 ranges are refused unless named explicitly**; (c) names through a resolver (section 26 names it "the next piece to build if names matter"). **Chosen (b) with the policy still "refuse, don't downgrade"** (a bad host stops the start or is a `400`), in S3. **Names remain unsupported**, which is a real cost for a Kubernetes deployment (a ClusterIP is stable for the life of the Service, so it is workable, not pleasant); (c) is the open question. The `path` and `host_header` per endpoint (D7) are validated by the same parser: printable, no space, a path that starts with `/`, no `#`, at most 255 bytes.

### D18. A stuck cursor must not stall the other endpoints: a prerequisite slice. (to confirm)

2.4: `extend_scan` is bounded by the slowest cursor, so one endpoint that stops advancing (a poison event, a down receiver, a `410` disable) stalls every endpoint after 1,024 events. For the outbound service that is a stated limit; **for a gateway whose receivers are other teams' services, it is the normal failure and it breaks the one promise that matters ("a slow, silent or unreachable endpoint costs the others almost nothing" is true for latency and false for a long outage).** Options: (a) **park** an endpoint whose cursor is more than the window behind the newest event: exclude it from `lowmark`, keep its cursor and cells, and give it the old events back by `seek_after(cursor)` (which exists, linear) when it recovers: no loss, the events are in the log; (b) per-endpoint scan positions and offsets (the `offs` table becomes per slot: 62 x 1,024 more integers, 0.5 MB); (c) a bigger `span` (cells: 62 x `span` x 3 x 8 bytes, 1.5 MB now, 12 MB at 8,192; only moves the day, does not remove it); (d) status-aware dead-lettering: a `4xx` other than `408`, `425`, `429` is dead at once, as `410` already is. **Chosen: (a) first** (smallest change, same semantics as `disabled`), (d) as a per-route option (`dead_on_4xx = 1`, to confirm: a receiver that answers `400` today because it is deploying would lose events). Neither is built; both change the delivery state.

### D19. Metrics: `GET /metrics`, Prometheus text, behind the token; a loss is a counter.

`docs/design.md` section 5 planned `/metrics` and it was never built (the README table has `GET /stats` only). Counters per source (at most 64 labels): `received`, `verified`, `stored`, `rejected{reason=bad_signature|stale|malformed|unknown_encoding|too_large|rate_limited|budget|paused}`, `deduped`, `dedupe_conflict`, `dedupe_skipped`, `challenge`, `headers_dropped`; gauges: events accepted (last id), per endpoint the cursor lag (last id minus cursor), parked endpoints, disabled endpoints, waiting replays, idempotency keys held, the log's size and whether it is broken, `history_*` as in `/stats`. Counters are in memory (a restart resets them; Prometheus handles resets). **Alert on:** `rejected{too_large}` > 0, `rejected{bad_signature}` rate, cursor lag growing, the log broken, the disk. A `413` or a `401` for a real provider is a webhook the provider may never resend.

### D20. A request is `Content-Type`-agnostic and `Host`-agnostic.

The gateway serves `POST /in/:token` for any `Content-Type` (D6) and any `Host`; `GET /in/:token` is `405` with `Allow: POST` (the router's existing behaviour for a known path and another method).

## 5. Data model

### 5.1 PostgreSQL (S6; the file forms of S1 to S5 carry the same fields)

```sql
-- Added to sql/schema.sql; the service does not create them (as for attempts and endpoints).

-- The endpoints a source's webhooks may be forwarded to are the existing `endpoints` rows, with two more columns.
alter table endpoints add column if not exists path text not null default '/hook'
    check (path ~ '^/[!-~]*$' and length(path) <= 255);
alter table endpoints add column if not exists host_header text;          -- null: what request_for sends today ("receiver")

create sequence if not exists source_ids minvalue 1 start 1;

create table if not exists sources (
    id integer primary key check (id between 1 and 999999),             -- what the log's `src` pair and the API call it; never reused
    name text not null unique check (name ~ '^[a-z0-9][a-z0-9_.-]{0,62}$'),
    kind text not null check (kind in ('github', 'stripe', 'shopify', 'slack', 'hmac')),
    token text not null unique check (length(token) between 22 and 64), -- the path component of /in/<token>: an identifier, not an authority
    secret text not null,                                                -- the provider's signing secret, IN THE CLEAR (the service computes the HMAC): permissions of a secret
    prev_secret text,                                                    -- accepted until prev_until_ms (rotation overlap)
    prev_until_ms bigint,
    status text not null default 'active' check (status in ('active', 'paused', 'deleted')),
    tolerance_s int not null default 300 check (tolerance_s between 1 and 3600),
    dedupe boolean not null default true,
    rate_per_s int not null default 50 check (rate_per_s >= 0),         -- 0: no limit
    burst int not null default 200 check (burst >= 0),
    -- kind = 'hmac' only (null for the four named kinds)
    sig_header text, sig_prefix text, sig_encoding text check (sig_encoding in ('hex', 'base64')),
    ts_header text, signed_as text check (signed_as in ('body', 'ts.body')),
    dedupe_header text, type_header text, extra_headers text            -- up to eight names, comma separated
);

create table if not exists routes (
    id integer primary key,
    source integer not null references sources (id),
    endpoint integer not null references endpoints (id),                 -- endpoints.id is an integer (section 25.1)
    types text,                                                          -- null: every type; else exact names, comma separated
    since_event bigint not null,                                         -- the last event id when the route was made (D10): a route never starts in the past
    signing text not null default 'both' check (signing in ('both', 'provider', 'standard')),
    dead_on_4xx boolean not null default false,
    enabled boolean not null default true,
    unique (source, endpoint)
);
```

At most **64 sources** and **62 endpoints** (the delivery state's slots: one integer's bits for `disabled`), so at most 62 destinations *in all*, shared by every source; a gateway with five providers each fanned out to four internal services uses 20. (An open question: is 62 enough?) The service reads both tables **once at start**, writes them as the text its parser takes (as C3c does for `endpoints`, with the same per-field printable check, so a newline in a header name cannot become a second row), and refuses to start on a row it cannot use (status 20 and 13 as in section 24.1). `attempts` is unchanged. An optional `inbound_events (id bigint primary key, source int, received_ms bigint, typ text, bytes int, dedupe_key text)` for "what did Stripe send last night" is best-effort like `attempts`, through the same ring and pool (S7); **the log stays the truth** (section 24).

### 5.2 Files, for the first slices

`<dir>/sources.conf`: `<id> <kind> <token> <secret> [key=value ...]` with the options named like the columns; `<dir>/routes.conf`: `<id> <source> <endpoint> [types=a,b] [signing=both] [since=N]`. `#` comments, a bad line refuses the start (as `endpoints.conf`). With `pg-host` they are not read.

### 5.3 The `events.seg` record for an inbound event

Same framing as every record (`len crc ms seq fields`, then pairs). **Pair order is fixed, and the first pair is the body**:

| # | name | value | when |
|---|---|---|---|
| 1 | `event` | **the raw body**, byte for byte | always |
| 2 | `src` | source id, 8 bytes little-endian (as `t` is) | inbound only |
| 3 | `hdr` | the allow-listed headers as `Name: value\r\n` lines, at most 4,096 bytes | inbound only |
| 4 | `typ` | the event type text, at most 128 bytes (empty if unknown) | inbound only |
| 5 | `key` | `<source id>:<provider key>` | only if there is one |
| 6 | `t` | received time, Unix ms, 8 bytes | always for inbound |

An outbound event is unchanged (`event`, or `event key t`). The reader tells them apart by **names, never by field count** (the change to `rebuild`, the first thing S0 does): a record with a pair named `src` is inbound. The size of a record is `28 + (13 + body) + 19 + (11 + hdr) + (11 + typ) + (11 + key) + 17`, which is **110 bytes plus the body, the headers, the type and the key**; `len` is that total less its own 4, so the limit is `body + hdr + typ + key <= 65,430`: about 61,000 body bytes with every cap hit (4,096 of headers, a 128-byte type, a key of about 64), about 64,700 with ordinary headers.

**Is the received request recoverable from the record?** The body and the allow-listed headers, yes. The query string, the request line's path (the token, deliberately), the client address and the dropped headers, no, by design.

## 6. The ingest path and why it cannot lose an acknowledged webhook

`POST /in/:token`, in `handle`, in this order. Each numbered failure **appends nothing**:

1. Route; the source by token in constant time, else `404`. Source `deleted` -> `410`, `paused` -> `503` + `Retry-After`.
2. Server-level: more than 64 headers `400`, a head and body over 69,632 bytes `413` (before `handle`).
3. Per-source bucket and the global verification budget: `429` / `503` with `Retry-After` (D14).
4. `Content-Encoding` present and not identity: `415` (D6). Required signature material missing or the wrong shape: `400`. A stale timestamp (`stripe`, `slack`, timestamped `hmac`): `401`.
5. HMAC and the constant-time compare (current secret, then the previous within its time): no match, `401`, a counter, nothing logged but the source and the reason.
6. **Verified.** A Slack `url_verification`: answer the challenge, store nothing.
7. Extract the dedupe key and the type (D9, D11); the key is `<source>:<provider key>`. If the key is held and fresh: the event is a duplicate; note the existing id, **answer after the flush** exactly like a new event (the path outbound idempotency already has, section 17), store nothing.
8. Build the record (5.3) and `log.append`: `too_long` -> `413`; any other failure -> `503`. If the key is new, insert it in the index **only after** the append succeeded (the order that keeps the index from holding a key the log does not). A full index: store without the key (D9).
9. `note[0]` = the id; `run` holds the connection. After the turn's last request: **one `log.flush`**; if it answers 0, each held request is answered `200 {"id":N}`; if not, `503` and the log refuses everything after.

**The argument, by the cases a crash can fall in** (the same argument as `docs/design.md` section 13, with one more step before the append):

* *Before step 8:* nothing was written; the provider got no `2xx` (or a `4xx`/`5xx`); whatever it does on a non-`2xx` it does (3.2).
* *After the append, before the flush:* the record may or may not be on disk; **no `2xx` has been sent** because the answer is given only after the flush; recovery (`log.recover`) truncates a torn tail to the last whole record, which can lose only unacknowledged records (`lexsys-log` design section 6: a bad record cannot lie below the durable point). The provider retries (or, GitHub, does not: the event was never acknowledged, and is a loss the gateway never promised against).
* *After the flush, before the `2xx` reaches the provider:* the event is durable and the provider retries, so it arrives twice; step 7 recognises the key (rebuilt from the log at start, so it survives the crash: the property `tests/idempotency_test.py` pins for keys) and answers the same id. With `dedupe = 0`, or when the index was full, it is stored twice: a duplicate, never a loss.
* *Flush fails (disk full, I/O error):* the log marks itself broken (`log.flush`), every held request is `503`, and the log refuses everything until a restart; a record that reached the disk anyway is, after the restart, a stored event whose acknowledgement was never given: a duplicate on retry (deduplicated, if keyed). **For a public endpoint a broken log is a total outage, and a restart is the repair**; monitor the disk and `503`s (D19).
* **The mutants that matter are the order ones:** acknowledge before the flush; flush after the acknowledgements (the worse symptom, reused ids); verification skipped; **the append before the verification** (a bad signature then stores a record: the "a bad signature stores nothing" gate catches it by comparing `events.seg` byte for byte).

**`401`, `400`, `404`, `413`, `415`, `429` and the `503` of the budget never touch `events.seg`.** A bad signature's only footprint is a counter and a log line without the body.

## 7. Byte-exact forwarding

* **The body.** The attempt's request is built from the record's first pair (as `start_one` does) and sent with `Content-Length` equal to its length; **no re-serialisation, trimming, charset conversion or newline handling anywhere**: the bytes the receiver gets are the bytes the provider sent, including `NUL`, `CR LF`, a UTF-8 BOM and a missing final newline. The test is a hash: SHA-256 of the body the receiver gets equals SHA-256 of the body the provider sent, over a corpus (empty, one byte, 55/56/63/64/65 bytes, every byte value, 65,000 bytes, JSON, form-encoded, a body that is invalid UTF-8).
* **Headers:** the stored lines (D7), `Content-Type` as stored, then `webhook-*` (D8), `X-Hooks-Source`, `Content-Length`, `Connection: close`. **Never forwarded:** the hop-by-hop set, `Authorization`, `Cookie`, `Proxy-*`, `X-Forwarded-*`, `Host` (replaced by the endpoint's), `Content-Length` (recomputed), `Transfer-Encoding` (the server dechunked; we send a length). A header is forwarded **as received** in name case and value; only the whitespace around the value is the parser's.
* **The signing modes** (D8): `both` adds the three Standard Webhooks headers to the stored ones; `provider` adds none; `standard` removes the provider's signature and timestamp headers (`X-Hub-Signature*`, `Stripe-Signature`, `X-Shopify-Hmac-Sha256`, `X-Slack-Signature`, `X-Slack-Request-Timestamp`, the configured `sig_header` and `ts_header`).
* **The request must fit the slot:** `attempt.req_max()` (66,560) minus the request line and headers; a record whose request does not fit is a failed attempt (`no_send`) that retries to a dead letter, which is a silent loss path; so **the gateway refuses at ingest a body that could not be forwarded** (`413`), by making the ingest limit `req_max()` minus the worst-case forwarded headers (4,096 stored + about 400 for ours + the path and host), about 61,700 bytes, until the buffer is raised together with `L` (D13). This makes the real limit about 61,700 (not the record's 61,000 to 64,700: the smaller of the two applies) and it must be documented as that number.
* **Replay** re-sends the stored request through the same builder: the stored body and headers and a **fresh** Standard Webhooks timestamp; a receiver verifying the provider's timestamped signature will reject a replay or a retry older than the tolerance (D8).

## 8. Fan-out, filters and ordering

D10 and D11 are the design; D12 says what is not guaranteed. The routes decide, per event and endpoint, whether the event is wanted; for a wanted one **everything after that is the existing machinery**: window, retries, `410`, dead letters, history, replay. One source to several destinations is several routes with the same source; several sources to one destination is several routes with the same endpoint and **one path** (the path is the endpoint's: a destination that wants Stripe at `/stripe` and GitHub at `/github` is two endpoint rows, which counts twice against 62).

## 9. History and attempts

`attempts` and `GET /events/:id/attempts` work unchanged (by event id). `GET /events/:id` gains, for an inbound event, `{"id","source":"<name>","type","received":<ms>,"headers":[...],"event":...}` with the body as a JSON string when it is not JSON (base64 for a body that is not UTF-8) and **the provider signature headers redacted from the answer** (not from the record: the signature of a captured request is what replays it, so it is not served). The response is behind the token (D2). `GET /events` listing by source and time needs the optional `inbound_events` table (5.1) and is S7.

## 10. Reused and new

**Reused unchanged:** the log and group commit, recovery and the fsync-shim crash harness; the idempotency index (with the S0 changes); the delivery state, windows, cursors, retry schedule, `410` disabling, dead letters; the non-blocking attempt machinery (64 in flight); Standard Webhooks signing and its 536-check oracle; replay; the `attempts` history and its API; `endpoints` management with the admin token, `mg`, and "database first, memory on commit"; settings; the SSRF parser (extended). **New:** the sources and routes (file, table, parse, management); the inbound handler and the five verifiers; hex decoding and the constant-time compare; the named-pair record and the `rebuild` change; the per-endpoint path and host; the header allow-list; `wanted`, the `meta` array and the `advance` record; dedupe reclaim and fail-open; the buckets and the budget; `/metrics`; `allow-cidrs`; the parking of a stuck endpoint. New code goes in **new modules** (`inbound.ls`, `verify.ls`, `routes.ls`, `sources.ls`), not into `hooks.ls`, which is already 2,803 lines.

## 11. Operations in one place

TLS and request buffering in a reverse proxy (D15); `inbound = 1` and an `admin-token` (D2); a data directory on a disk that is watched (`events.seg` and `delivery.seg` **grow without bound**: the arithmetic for 100 events a second of 5 KB each is about 43 GB a day of events and, for ten destinations, the outcome records of one attempt each, 77 bytes: a retention and compaction story does not exist and is the gap between this design and any production use); `allow-cidrs` for the receivers; one process, so a restart is the repair and the providers' retries are the buffer (except GitHub's). The service **does not** (S0 to S7) deliver faster than one core: the verification budget (D14) is what keeps the core shared.

### S0. Prerequisites (behaviour-neutral)

**Gate.** Every existing suite passes unchanged (`chaos.py`, `delivery.py`, `idempotency_test.py` with `FULL=1`, the unit tests, `sign_test.py`'s 536 checks). A log written by the current binary is read by the new one with the same state. A record with the six pairs of 5.3 is read by `rebuild` (a keyed inbound event enters the index, an unkeyed one does not, a pair out of order is refused with 16, as a malformed record is today). **70,000 distinct keys fed through a simulated clock are never refused** once the first 65,536 have expired (today: `507` from the 65,537th); a full index of *live* keys stores the event without the key and counts `dedupe_skipped`. Hex: every length 0 to 70, both cases, against Python's `bytes.fromhex`, and eleven malformed inputs. Constant-time compare: equal and unequal inputs, differing first, last and middle byte, lengths 0 and 32 (the result is the same function of the inputs). **Parked endpoint (D18):** one of three endpoints answers `400` to event 1 forever; after 3,000 events the other two have delivered all 3,000, the stuck one has 1,024 in its window and is parked, and when its receiver is fixed (its answer changes) it receives events 1 to 3,000 once each, in a restart too (the case 25.3's `8b` is for the new-row version of this).

**Mutants.** `rebuild` still counting fields; accepting a pair out of order; the reclaim freeing a live key, or freeing an expired one a tick early; the fail-open still `507`; hex accepting a short or odd input, accepting a non-hex byte, case-sensitive; the compare returning early (see D14 for how that is, and is not, caught); the parked endpoint kept in `lowmark`; parked but never resumed; resumed from the wrong cursor.

### S1. The generic HMAC source

**Gate.** (1) **Kill -9 loses no acknowledged event:** `tests/chaos.py`, extended to post signed `/in` requests from eight threads under power cuts (the fsync shim) for 2,000 events and at least 100 kills; its independent reader checks **every acknowledged id has the exact body, the exact stored headers and the right source** in the valid prefix. (2) **A bad signature stores nothing:** for each failure class (wrong secret, one bit flipped in the signature, one byte changed in the body, a signature of the right length for another body, a stale timestamp, a future timestamp, a missing header, a malformed header, a wrong token, an unknown content-encoding, an oversize body) 200 requests each, then `events.seg` is **byte-identical** (its SHA-256 and size equal to before) and `delivery.seg` too, the status code is the expected one, and the per-source counter for the reason moved by exactly 200 and no other did; stderr contains no byte of any body or signature. (3) **No body in the log of a failure:** the harness greps stderr and the `/metrics` text for a canary string placed in every body and header. (4) Acknowledgement is after the flush: a `200` is never seen for an id above the log's synced mark (the flush-order mutant dies here as in section 13). (5) A `200` within **500 ms p99** at 200 requests a second for 30 s with one `hmac` source (reported, gated at that figure; Slack's 3 s is the budget, and this is a sixth of it). (6) An unknown token costs a lookup and no cryptography: after 5,000 unknown-token requests the service's HMAC work counter (a test-visible counter of bytes MACed) has not moved, and every answer was `404`.

**Mutants.** Acknowledge before the flush; flush after the acknowledgements; **append before verifying**; verification skipped; a mismatch accepted when only the lengths are equal; signed content without the `.`; the timestamp compared without `abs` (future accepted); tolerance `>=` for `>`; the prefix not stripped; hex case; header lookup case-sensitive; **duplicate signature header accepted (first wins)**; the stale check after the HMAC (functionally equal, killed by the work-counter gate of D14 only); the body modified before the MAC (a trailing newline trimmed); the record's `src` the wrong source; the stored `hdr` not the request's.

### S2. The four providers

**Gate.** The **providers' published vectors verify**: GitHub's (`It's a Secret to Everybody` / `Hello, World!` / `sha256=757107...3e17`, checked here against Python) and Slack's (the python-slack-sdk test's, secret `8f742231...85a5`, timestamp `1531420618`, the body in that file, `v0=a2114d57...b503`, with the clock fixed or the tolerance widened for the test) are accepted, and every one-bit mutation of each is refused. For Stripe and Shopify, which publish none that I found, **the vendors' own SDKs are the oracle**, as the reference `standardwebhooks` library is for outbound signing (section 15): `stripe-python`'s `WebhookSignature` generates and verifies the header (this is where the **key handling of `whsec_`** is settled: text or decoded), and Shopify's validation is checked against Python's `hmac` + `base64`; 300 random bodies per kind, lengths around SHA-256's block boundaries, the secret under, at and over 64 bytes; Stripe with one, two and three `v1`, with a `v0` first, with the matching `v1` last and with none matching; Slack and Stripe at the tolerance boundary (299, 300 and 301 s old and future). The Slack `url_verification` body gets the challenge back, stores nothing, and a counter says so. **Through a real reverse proxy** (nginx with default settings) a signed request still verifies for a body with every byte value, to show the proxy leaves the bytes alone (the point of D15). The rotation overlap (D16) verifies under both secrets and refuses the old after `prev_until_ms`.

**Mutants.** Stripe: only the first `v1` checked; `v0` accepted; `t` not part of the signed string; separator `.` missing; tolerance 301 or off by a unit; the secret decoded (or not) the wrong way. Slack: `v0:` missing from the base string; timestamp unchecked; the challenge answered for an **unverified** request; the challenge stored. Shopify: hex expected for base64; padding stripped; body trimmed. GitHub: `sha256=` optional; the SHA-1 header accepted as a fallback (**a downgrade: must be refused**); uppercase hex rejected. All: a signature accepted that is the MAC of a *prefix* of the body; a MAC compare of 31 bytes.

### S3. Forwarding

**Gate.** **The SHA-256 of the body the receiver gets equals the SHA-256 of the body the provider sent**, for the corpus of section 7, through ingest, the log, a restart, a retry and a replay. The receiver records the exact request: the stored allow-listed headers are present with their exact values and case; **no hop-by-hop header, no `Authorization`, no `Cookie`, no `X-Forwarded-*` is ever seen** even when the sender and the proxy put them there; `Host` and the path are the endpoint's; `Content-Type` is the sender's (a form-encoded body arrives as form-encoded). In `both` mode the receiver verifies the **provider's** signature (Stripe's with `stripe-python`, GitHub's, Slack's, Shopify's) for the first attempt, **and Standard Webhooks with the reference library** for the first attempt, a retry and a replay, and **the provider's fails after its tolerance on a retry and a replay, which the test asserts** (it is the documented behaviour of D8, so it must be a green test, not a surprise); in `standard` mode the provider headers are absent. A header value with a byte 0x80 to 0xFF round-trips. A request that would not fit a slot is refused `413` at ingest and never reaches the log. `allow-cidrs`: 41 refused and 23 accepted hosts as in section 26's test, with the metadata and loopback ranges refused unless named. **Kill -9 during forwarding** repeats nothing beyond the at-least-once repeats of section 14.

**Mutants.** The body re-serialised or trimmed; `Content-Length` from the wrong buffer; the fixed `application/json` instead of the stored type; a hop-by-hop header forwarded; `Authorization` forwarded; the `Host` not replaced; a header's case changed; `standard` mode leaving the provider signature; `provider` mode adding ours; the replay building from the wrong record; the path from the wrong endpoint; the request-fits check off by one; a CIDR boundary off by one; the loopback range allowed by default.

### S4. Dedupe

**Gate.** Per provider: the provider's key (header or body) deduplicates; a repeat after a kill answers the same id (the keyed chaos stage of `idempotency_test.py`, with `/in`); **the same key with a different body is `200` and stores nothing, and `dedupe_conflict` moves**; two sources with the same provider key do not collide; a source with `dedupe = 0` stores both; **70,000 distinct provider keys over a simulated clock lose none** (S0's reclaim, now through `/in`); a Shopify repeat with `X-Shopify-Webhook-Id` (or the key section 3 settles on) is one event; a GitHub redelivery inside the window is acknowledged and not stored, outside it stored. **Mutants:** the key not namespaced; a conflict answered `422`; the index inserted before the append; the reclaim freeing a live key; the namespace compared by prefix; fail-open dropping the event; the counter not moving on a conflict.

### S5. Fan-out and filters

**Gate.** Three endpoints, two sources, routes A<-s1, B<-s1 (types `push`), C<-s2: each endpoint receives exactly the events of its routes (and for B only `push`), **once each**, and nothing else; a route created after 1,000 events gets none of them and gets event 1,001; **across a restart** the same set (no event wanted is lost, no unwanted one is sent): the pure-function property; a route deleted while 50 events are pending drops them (and `drop=1` was required); **an endpoint that wants one event in 100,000 receives it after a restart in under 30 s** (the cost of re-walking skipped events, the reason for the `advance` record) with the `advance` mutants alive or dead as the gate says; the type filter by header (GitHub, Shopify) and by body (Stripe, Slack), with a type of 128 bytes, 129 bytes, empty and absent; `delivery.seg` grows by **no record per skipped event** (a size check after 10,000 unwanted events: under 2 KB). **Mutants:** `wanted` always true; `since_event` ignored or off by one; the filter `!=` for `==`; a case-insensitive type match; the `advance` record written past a non-final wanted event (the cursor leaps over an undelivered event: **the one that loses an event, and the first the gate must kill**); `advance` replayed with assignment instead of `max`; routes edited in place; a deleted route's events still sent; the `meta` cache not reset on ring reuse.

### S6. PostgreSQL, management, `inbound = 1`

**Gate.** Sources and routes from the tables, read once at start, every refusal (a bad row, no table, a token of 21 bytes, two rows with one token); `POST/GET/PATCH/DELETE /sources` and `/routes` behind the token as 25.2 to 25.4 (a missing, wrong, truncated token, no token configured, no database, a trigger that refuses and nothing changes, a database that takes seven seconds and a second change `409`); **the secret is in one answer and in no read, the token in the admin reads only**; **with `inbound = 1` every route but `POST /in/:token` and `GET /healthz` is `401`/`403` without the token, `GET /events/:id` included, and the service refuses to start without an `admin-token`**; a deleted source is `410` and its stored events still deliver; a paused one `503`; rotation overlap; a kill after the commit and before the memory change (the next start has the source). **Mutants:** the `inbound` check on one route removed (a test per route, every route enumerated from the router so a new one cannot be forgotten); a read that returns `secret` or `prev_secret`; the delete dropping events; the paused answering `200`; a source change applied before the commit; `since_event` not stored.

### S7. Limits and metrics

**Gate.** A flood of 20,000 maximum-size bad-signature requests (65,000 bytes) from one source does not move the **p99 of acknowledged ingest of a second source above 3x its baseline** and leaves delivery latency unmoved (the verification budget, D14); a source over its bucket is `429` with the header and recovers; `/metrics` counts match what the harness did, exactly, for every reason (the "increments the wrong counter" mutant dies here); `rejected{too_large}` moves for a `413`. **Mutants:** the bucket per service instead of per source; the budget not reset per turn; the bad-signature threshold never resetting; a counter shared by two reasons; `Retry-After` missing; the budget answering `401`.

## 13. Risks, honestly

1. **D18 (a stuck cursor stalls all endpoints after 1,024 events) is derived, not re-measured, and is the largest risk.** Until it is built the gateway is for a handful of well-behaved receivers.
2. **No retention, no compaction, linear lookups** (`events.seg`, `delivery.seg`, `find_event`, `find_offset`): growth at gateway rates is arithmetic, not measured (11); `GET /events/:id` is a linear scan of a log that never shrinks.
3. **One thread, one core.** A 65 KB HMAC is 1.2 ms (measured); the budget (D14) bounds the damage to the other work but not the total: roughly 800 verifications a second at the maximum size, about 1,800 at 16 KB, about 4,000 at 1 KB (from the three measured points), on the core that also does everything else.
4. **GitHub does not retry** (V1): every webhook it sends while the gateway is down, broken or over a limit is gone. The promise is "acknowledged is durable", and the operator documentation must open with it.
5. **A 413 is a loss for GitHub and a loop for the rest**, and the real payload sizes of Stripe, Shopify and Slack are NV (D13).
6. **The outbound hop is plaintext HTTP to IP literals** (no TLS, no names): the payload with customer data crosses the internal network unencrypted; the Kubernetes case is awkward (D17).
7. **Secrets in the clear in PostgreSQL**, now of two kinds (endpoint signing secrets and provider verification secrets); read access to `sources` forges provider events into the gateway (D16).
8. **A header allow-list is a guess about what receivers use**, per provider; the `hmac` kind carries a configurable list, the four named ones do not, and a missing header is a bug report, not an error.
9. **`both` signing invites the wrong verification** (D8): documentation and an example receiver per provider are part of S3, not an afterthought.
10. **The `events.seg` upgrade is one-way** (D1) once a source exists.
11. **Provider facts marked NV and V2 may be wrong or changed** (3.3). The gates use the vendors' SDKs and published vectors precisely so that the verifiers are not tested only against this document's reading.
12. **The test for constant-time compare is structural** (D14): an early-exit mutant is behaviourally equal.
13. **`hooks.ls` is 2,803 lines and the delivery-state layout is a chain of computed offsets that has already hidden one overlap bug** (section 25): the `meta` array, a `src` per window cell, and a larger `mg` block each add regions to it; the layout test (`tests/layout_test.py`) must grow with each.
14. **My own reading of two vendor details is not tested here**: that Stripe's key is the secret text and not its decoded form (D4: settled by the S2 gate against `stripe-python`, not assumed), and that GitHub's hex is lowercase only (accepted in both cases here; the docs example is lowercase).

## 14. Open questions, for a person

1. **D1.** Is a one-way upgrade acceptable (the old binary refuses a log with inbound records)? If not, the alternative is a second log and the two-store problem.
2. **D2.** Is `inbound = 1` with a token on every other route right, or do you want the two-listener change in lex-sys (the clean one), or to rely on the reverse proxy and accept an open `GET /events/:id` behind it?
3. **D8.** Is `both` the default you want? Which receivers verify what? For Stripe and Slack the provider's signature stops verifying after five minutes on any retry or replay; is that acceptable for the receivers, or should the default be `standard` (receivers change) or `provider` (retries and replays will fail at the receiver)?
4. **D9.** (a) Dedupe on by default for GitHub, at the cost of swallowing a manual redelivery inside the window? (b) For Shopify, `X-Shopify-Webhook-Id` or `X-Shopify-Event-Id` (to be settled from shopify.dev's "ignore duplicates" page, which I could not read)? (c) A repeat with different bytes is `200` and stored once: is "first writer wins" right for Stripe?
5. **D10.** Routes start from now and are immutable; a deleted route drops its pending events, with `drop=1`. Is that the delete you want, or should a delete drain first?
6. **D13.** Keep 65,536 (about 62,000 forwardable) and count the `413`s, or is there a known source (a large `push`, a big Shopify order) that needs more from the start, in which case the spill design is the next document?
7. **D14.** The numbers (50 a second, burst 200, a 4 MB verification budget a turn, 300 s tolerance, never 0): what are your providers' real peaks (a Shopify flash sale, a Stripe batch)? A bucket too low loses a GitHub webhook.
8. **D16.** One admin token for endpoints and sources, or a second for sources? A route delete that drops events and a source delete that stops ingest: right?
9. **D5.** Does Slack sign the `url_verification` request? If it does not, setup needs the challenge answered before the signature check, which is harmless (it reflects a string) but a change to D4's order.
10. **D17.** `allow-cidrs` instead of `allow-private-hosts 1`, and names unsupported: is a resolver (design section 26's "next piece") needed before this is usable in your network?
11. **D18.** Parking a stuck endpoint (a) and optional `dead_on_4xx` (d): which receivers answer `4xx` for what is only a temporary condition?
12. **62 destinations and 64 sources in all** (the `disabled` set is one integer): enough?
13. **Missed webhooks.** GitHub does not retry and the gateway will have gaps whenever it is down. Do you want a puller (GitHub's and Stripe's APIs list recent deliveries and events) as a later slice? It would turn "acknowledged is durable" into "nothing is lost" for those two, at the cost of two more provider-specific integrations with credentials.
14. **Retention.** Nothing here removes an event. What is the retention you need, and is the gateway acceptable "not for production" until `lexsys-log` has compaction?
15. **Naming.** `POST /in/:token`, `X-Hooks-Source`, `signing`, `since_event`: any conflict with names your receivers already use?
