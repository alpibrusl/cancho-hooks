lexsys-hooks

Webhook delivery you can reason about. Post an event once; it is on disk before you get the answer, and every subscribed endpoint receives it, signed, at least once, through crashes, slow receivers and a database that goes away.

A single binary written in lex-sys, a typed systems language with linear ownership and capability effects. Its logs, its PostgreSQL client and its name resolver are lex-sys too, and what the program may do is a report the compiler writes and CI pins.

What it does

Durable ingest, idempotent

POST /events appends to a log and answers after the flush. Send the same Idempotency-Key again and you get the first answer back, byte for byte, also across a crash.

Retries, dead letters, replay

The Standard Webhooks schedule, spread by jitter, then a dead letter. List an endpoint’s dead letters, replay them in bulk, replay any event to one endpoint or all, cancel a replay that waits.

One bad endpoint stays one bad endpoint

Attempts never hold the loop; each endpoint reads the log from its own cursor, with its own concurrency and rate. A circuit breaker pauses an endpoint that has failed for days.

Per endpoint

Event-type subscriptions (invoice.*), custom headers whose values are never read back, and secret rotation with both signatures on every delivery while the overlap lasts.

Managed while it runs

With PostgreSQL, endpoints are a table you change through the API, every ended attempt is a history row (best effort), and cron schedules append ordinary events exactly once, even when the service is killed mid-fire.

Safe defaults where they matter

Scoped tokens on every route; production = 1 refuses to start until nothing is left open. By default deliveries go only to public addresses, checked at every attempt; https verifies the chain and the name, with no switch to turn that off.

Operable

/readyz says which check failed; Prometheus /metrics; the reason every attempt failed; a graceful stop; backup and restore, online or stopped; a Dockerfile and a systemd unit.

Bounded, and honest about damage

Retention drops events only when they are final everywhere and old enough. A log damaged in the middle is refused at start with where and how much, never repaired silently.

How it works

One process, one thread, one poller: ingest and delivery run in the same loop, and two logs on disk are the truth about delivery.

  1. Ingest. The event is appended to the events log and its request is held.
  2. One flush per turn. After each turn of the loop a single flush covers every append; only then are the held requests answered 202.
  3. Attempts that never block. Each attempt is a small state machine on the loop’s poller: up to 64 in flight, 8 per endpoint.
  4. Signed delivery. POST to the endpoint with webhook-id, webhook-timestamp and webhook-signature; any 2xx is a delivery.
  5. Every outcome logged. Delivered, failed (with the time of its retry) or dead is appended to the outcomes log, so a restart resumes exactly where it was. With a database, each attempt is also a history row.

Send an event

curl -H "Authorization: Bearer $INGEST" \
     -H "Idempotency-Key: order-7-paid" \
     -d '{"type":"order.paid","order":7}' \
     https://hooks.example/events
{"id":41}            # after the flush, not before

Verify it at the receiver

from standardwebhooks import Webhook

wh = Webhook("whsec_...")
wh.verify(body, headers)   # raises if forged or stale
# webhook-id is the same on every attempt:
# drop a repeat by it

Why it exists

Written in lex-sys, with its authority on record

lexsys-hooks is the proving ground of lex-sys: a real service, held to a production standard, so that what the language and its libraries lack shows up and gets fixed where it belongs. No unsafe; memory is owned linearly and released by regions; every effect a function has (the file system, the network, a signal) is in its type.

The compiler writes an authority report: every capability the program holds and every foreign function it can call. It is committed (authority.json) and CI fails on any difference, so a new foreign call is a diff a person approves.

The default build

34

foreign functions: two of libc (reading the data directory’s mode, and asking for small pages once at start) and 32 of OpenSSL for https delivery.

hooks-pure

2

foreign functions, both of libc: https uses lex-sys’s own TLS. Built and tested beside the default; not the default until that TLS has been independently reviewed (pure-tls.md).

lex-sys all the way down

0

C libraries for the logs (lexsys-log), the PostgreSQL client with its SCRAM login (lexsys-pg), the name resolver, HTTP and the signatures.

The aim is a report with no foreign function at all; each one left is a gap in lex-sys with an issue of its own (a file-mode builtin, lex-sys#243, would remove the first).

Tested from the outside

The real binary, driven over HTTP by test programs that break things around it and check the result from the receivers’ side and from the files, with readers of their own. Nothing relies on the service’s account of itself.

  • kill -9and simulated power cuts, at random instants and at every numbered step of a compaction: no acknowledged event lost
  • 548signature comparisons against the reference Standard Webhooks library, at every block boundary
  • 50harness programs in CI, with misbehaving receivers, a proxy that cuts, freezes and black-holes the database, and a name server of their own
  • 226unit tests written in lex-sys, among them the cron calendar for 80,000 days and a million damaged DNS answers
  • mutantsfor each new piece of code, each one edit, each killed by a test or argued for in the design document
  • 1,024endpoints through five starts and four power cuts, every acknowledged event reaching every endpoint, signed with its own key

What it is not (yet)

  • Not for production. Before that line is lifted: a soak of at least 24 hours under chaos, with its numbers published, and the capacity figures it gives. The harness and its criteria are built and written down in advance (soak.md).
  • OpenSSL in the default build, until lex-sys’s own TLS has been independently reviewed.
  • One process, one thread, one core; at most 1,024 endpoints; no strict ordering; a host name for PostgreSQL is resolved with a call that waits (give an address).
  • The database is the trust boundary: signing secrets and header values are stored in the clear. No TLS on the service’s own port (put a reverse proxy in front), and a token changes only with a restart.
  • Packaging is young: the binary is a CI artifact for Linux x86-64; releases are not signed yet.

The full list, with what each limit was measured as: status.md.

Quick start

Build the pinned lex-sys compiler, then the service. You need git, Rust, gcc, OpenSSL 3 with its development files and Python 3.

git clone https://github.com/alpibrusl/lex-sys
git clone https://github.com/alpibrusl/lexsys-hooks && cd lexsys-hooks
REV=$(sed -n 's/^lex-sys *= *"\(.*\)"/\1/p' lex-sys.toml)      # the compiler these sources need
(cd ../lex-sys && git fetch -q origin && git checkout "$REV" && cargo build --release -p lex-sys)
export LEX_SYS=$PWD/../lex-sys/target/release/lex-sys
scripts/build.sh                                                # build/hooks

mkdir -p /tmp/hooks-data                                        # one endpoint: <id> <host> <port> <secret>
echo "0 127.0.0.1 9100 whsec_$(head -c 24 /dev/urandom | base64)" > /tmp/hooks-data/endpoints.conf
build/hooks --port 8080 --dir /tmp/hooks-data --allow-private-hosts 1 &
curl -d '{"type":"user.created","id":7}' localhost:8080/events   # {"id":1}

The README adds a receiver that verifies each delivery; security.md says how to close it with tokens and production = 1.
