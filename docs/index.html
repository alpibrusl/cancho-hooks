lexsys-hooks

A webhook delivery service, written in lex-sys. You POST it an event; it stores the event durably and delivers it, signed, to every configured endpoint, at least once, retrying on a schedule and keeping what it could not deliver as a dead letter.

It keeps its two logs in lexsys-log and talks to PostgreSQL through lexsys-pg, with no unsafe and foreign authority only through Ffi, by library, for the symbols docs/authority.json lists, pinned in CI: libc’s statx (the mode of the data directory, for the production profile; lex-sys has no file-mode builtin, lex-sys#243) and 32 functions of OpenSSL (libssl and libcrypto), for delivery to https endpoints. Learning that it was asked to stop needs no foreign code: it is a claim on SIGINT and SIGTERM that the authority report names. The repository’s design document records what each step built and measured, including what failed.

What it does today

Durable ingest

An accepted event is appended to a lexsys-log segment and answered 202 only after the flush. Requests that arrive together share one flush (group commit).

Signed delivery

Each delivery is a POST /hook with webhook-id, webhook-timestamp and webhook-signature (HMAC-SHA256, v1, and base64). Any 2xx is a delivery.

Retries and dead letters

Failures retry on the Standard Webhooks schedule, each delay moved by up to retry-jitter percent (10 by default, 0 is the schedule exactly) so that events that failed together do not all come back together; after the last retry the event is a dead letter for that endpoint. Every outcome, with the time of the next attempt, survives a crash.

List and replay dead letters in bulk

GET /endpoints/:id/dead lists an endpoint’s dead letters (event, type, attempts, why the last attempt failed, when it died), newest or oldest first, paged by an event-id cursor. POST /endpoints/:id/replay-dead sends them again, as many at a time as the 32 waiting replays have room for, and says how many it took and how many remain; a waiting replay can be taken back with DELETE /events/:id/replay/:endpoint or all of an endpoint’s with DELETE /endpoints/:id/replays, and the cancellation survives a crash and a power cut.

A pace for each endpoint

Each endpoint can be given a concurrency (1 to 8 attempts in flight) and a rate (attempts started a second), as a default for all (endpoint-concurrency, endpoint-rate) or of its own. An event held back by the rate waits; it is not a failure: no attempt, no retry counted, and the other endpoints are not slowed.

Idempotency keys

Send the same Idempotency-Key with the same event and you get the first answer back, byte for byte, and nothing more is stored, also across a crash.

Replay, and 410 Gone

POST /events/:id/replay sends an event again to one endpoint or all, with the same webhook-id. A 410 Gone dead-letters the event and disables the endpoint until you enable it.

One slow or dead endpoint does not stall the rest

Delivery attempts do not hold the loop: up to 64 are in flight, 8 per endpoint, so a slow, silent or unreachable endpoint costs the others almost nothing. Each endpoint reads the events log from its own cursor and is bounded only by its own window of 1,024 events. This was not always so: an endpoint 1,024 events behind used to stop every endpoint (a healthy one ended at 1,024 of 3,000 beside a dead one; §29), and now ends at 3,000 of 3,000 (§31). A circuit breaker pauses an endpoint whose every attempt has failed for 5 days (breaker-days, 0 is off); its events wait in the log until you enable it.

Event types, secret rotation, custom headers

An endpoint can subscribe to a list of event types (invoice.paid, user.*): it is sent only those, and an event it does not want is final for it at once, with no attempt, so a stream nobody wants holds nothing back. A secret can be rotated with the old one kept valid for a stated time: every delivery then carries both signatures (v1,<new> v1,<old>), so a receiver that knows either verifies it. An endpoint can have up to 8 custom headers, such as an Authorization; the values are never returned by a read, and the headers the delivery sets (webhook-*, host, content-length, content-type, connection, transfer-encoding) can never be set.

PostgreSQL, optionally

With --pg-host, endpoints are the rows of an endpoints table and every ended attempt is a row of attempts, read back at GET /events/:id/attempts. With an admin-token an endpoint can be created, changed or deleted while the service runs.

Cron: scheduled events

With a database and an admin token, a schedule (POST /schedules: a five-field cron expression, UTC, an event type and a body) appends an ordinary event at each scheduled second under the key cron:<id>:<second>, so it is delivered, signed, retried and replayed like any other and is made exactly once even if the service is killed in the middle of a fire. After a stop it fires once for what it missed.

Tokens on every route, and a profile that refuses to be unsafe

Three bearer tokens (ingest, read, admin) say who may call what; GET /healthz and GET /readyz are always open, and GET /metrics needs the read token when one is configured. With production = 1 the service refuses to start, with a status and a message for each cause, unless the admin and ingest tokens are set and different, private destinations are off, and the data directory and its files are closed to the group and to others.

Watch it, and stop it

GET /readyz is 200 only when the logs are open and take a write, a named database has a live connection and the service is not stopping, and says which check failed when it is not. GET /metrics (a read-scope route: it needs the read token when one is configured) is the Prometheus text format: ingest, group commits, attempts by outcome, per-endpoint lag, retries waiting, the history, the logs’ sizes. SIGTERM or SIGINT stops taking requests and starting attempts, lets the attempts on the wire finish for at most stop-deadline-ms, flushes and exits 0; a second signal ends it at once.

Why an attempt failed

Each failed attempt records its reason with its outcome: connection refused, connection timeout, no response before the deadline, reset, closed early, a bad status line, a 3xx, 4xx or 5xx, 410 Gone, and for names and https a lookup that failed or timed out, a destination refused, a handshake that failed, a certificate that is untrusted, expired, for another name or otherwise invalid. It is in the delivery log, in GET /events/:id/attempts, in the history table, and counted in /metrics by reason, so a spurious failure can be told from a refusal after the fact.

Corruption is refused, not repaired silently

A log with damage in the middle, or a delivery log ahead of its events log, stops the start with a status of its own and a message that says where the log is whole, how many bytes cutting would lose and how many intact records are among them. Nothing is changed until you decide: --repair-logs 1 cuts the damage after copying the cut bytes to a file beside the log. The unfinished record a crash leaves at the end is still cut at start, and now reported.

Logs bounded by retention

The events log is a chain of segments, and a segment is deleted only when every event in it is delivered or dead-lettered at every endpoint and older than retention-days (30 by default). A paused, disabled or dead endpoint, or a waiting replay, keeps its events; the outcomes log is replaced by a snapshot of the state it replays to. With 3,000,000 events through one endpoint the data directory peaked at 95 MB, where the history would have taken about 1,002 MB. A dropped event is gone: GET /events/:id is a 404 and the same Idempotency-Key posted again is a new event.

https, and host names

An endpoint whose host is https://name is delivered to over TLS 1.2 or 1.3, with the certificate chain and the host name checked against the system’s trust store (or the one PEM file tls-ca-file names); no setting turns the check off, and every failure has a reason of its own. Host names are resolved by the service itself without holding the loop, and every address a name resolves to must be public (unless allow-private-hosts) at every attempt, with the connection made to the address that was checked. The TLS is OpenSSL, driven in the process (see “What it is not (yet)”).

A database that comes back

The service keeps two connections to PostgreSQL and remakes a lost one by itself, with waits that start at 100 ms and double to 5 s; /readyz is 200 again when one is live, with no restart. The start does not wait for the database: the service listens at once, takes events, and delivers once it has read its endpoints. Meanwhile the history rows wait in a queue of 256.

Backup, restore, packaging

scripts/backup.sh and scripts/restore.sh take and restore the two logs and the tables, stopped or online (the online variant under conditions the runbook states). A Dockerfile (non-root, under tini) and a systemd unit are in deploy/, and scripts/release.sh makes a tarball with checksums. The runbook says what each log line and metric means and what to do.

Small authority

No unsafe, and foreign authority only through Ffi, per library, for exactly the symbols docs/authority.json lists, 33 in all: libc, one function, statx, which reads the mode of the data directory for the production profile (in one small file, src/perm.ls; lex-sys has no file-mode builtin, lex-sys#243); and libssl and libcrypto (OpenSSL), 32 functions, the TLS client of an https endpoint (src/tls.ls): the context and the trust store, a connection over two memory buffers (no socket reaches OpenSSL), the handshake, reading and writing, the host name check, and the session kept for resumption. How the service learns it was asked to stop is a narrow capability of lex-sys, Signals("INT,TERM"): the report names exactly those two signals, and a stop wakes the event loop at once. OpenSSL is C code in the process, and the report cannot say what it does with the bytes it is given. The compiler’s authority report says bounded: false because the service calls foreign code, lists those symbols under unbounded_by (each with the library it is declared in): the labels bound everything except what those symbols do. The report is pinned in CI: docs/authority.json is committed and the build fails on any difference, so a new foreign symbol or capability is a diff that a person approves by committing the new file. The TLS of lex-sys itself (packages/tls) replaces OpenSSL when it can verify certificate chains; a file-mode builtin would remove the libc part.

How it works in one minute

One thread, one poller. Ingest and delivery run in the same loop.

  1. Ingest. POST /events takes a JSON object with a string "type". The event is appended to the events log and its request is held.
  2. One flush per turn. After the turn of the loop, a single flush covers every append. Only then are the held requests answered 202 {"id":N}.
  3. Attempts that do not block. Each delivery attempt is a small state machine (connecting, sending, reading) watched on the server’s own poller. Each endpoint has a cursor, a window of events above it, and its own place in the events log, so a failing event does not hold up the ones after it and a dead endpoint does not hold up another one.
  4. The request. POST /hook to the endpoint, event as the body, signed with the endpoint’s secret.
  5. The outcome. Delivered, failed (with the Unix time of the next attempt) or dead is appended to a second log, delivery.seg, with one flush per turn. A restart replays it, so counts and delays survive.
  6. Optional history. With a database, each ended attempt is also a row in PostgreSQL. The log files stay the truth about delivery; the history is best effort.

The retry schedule

Each delay counts from the previous attempt. A 2xx is a delivery; anything else, a timeout or a refused connection is a failure. These are the defaults, and the schedule setting changes them. Each delay is moved up or down by up to retry-jitter percent of itself (10 by default; 0 is exactly this schedule), by a fixed function of the endpoint, the event and the attempt, and the time chosen is written to the log, so a restart keeps it.

How the tests are built

The service is tested as a black box, with the real binary. A Python harness starts build/hooks in a temporary directory, drives it over HTTP, breaks things around it, and checks what happened from the outside; unit tests written in lex-sys itself cover the pure parts. Nothing about the tests relies on the service’s own account of itself.

  • Harnesses. 44 programs (tests/*_test.py, tests/chaos.py, tests/delivery.py) each start the service and drive it with real clients and real receivers. They read the result from the receivers’ side (in several of them a receiver verifies the signatures with the reference standardwebhooks library) and from the files, with readers of their own: tests/chaos.py reads events.seg with a reader written apart from the service, scripts/logcheck.py classifies a pair of logs, and tests/dead_test.py folds the delivery log itself.
  • Crashes, at chosen points. The service is stopped with kill -9 at random instants, when the receivers have seen a stated number of deliveries since the last start (the kills follow progress, not the clock), or at a numbered step of its own compaction, where it is told to wait and the test kills it.
  • Power cuts. A plain kill -9 cannot show a missing flush, because the kernel keeps every byte the process wrote. An LD_PRELOAD shim (tests/fsync_shim.c) records how long each log file was whenever fsync returned; before the restart the harness cuts each file to that length plus a random part of the rest, and may zero its last block: the data directory as a power cut could leave it.
  • The database. A TCP proxy (tests/pgproxy.py) between the service and PostgreSQL cuts the connections, refuses new ones, freezes both directions without losing a byte, black-holes new connections, and ends the backends of its own connections.
  • https and names. Throwaway certificate authorities and certificates made with the openssl command (expired, not yet valid, another name, another authority, self-signed, the wrong purpose), a TLS receiver that fails in a chosen way and reports what it saw, and a name server of the test’s own that answers what the test says and counts the questions.
  • Partial reads and writes. A second shim (tests/io_shim.c) makes send take only so many bytes, recv return only so many, and every third call fail with EAGAIN: the branches a loopback socket never reaches. It is used on the TLS receiver and the name server, not on a plain http receiver.
  • Receivers that misbehave. One that accepts and never answers, answers after 300 ms, closes without a word, resets in the middle of the response, answers garbage or a status line in two pieces, answers 500, 404, 301 or 410, reads a large request a few KiB at a time, has a full accept queue, or sits behind a blackholed address.
  • Mutation testing. For each piece of new code, mutants (one edit each, made on a copy of the tree) must be killed by a test; the design document gives, for each piece, how many were made and killed and every survivor with the argument for why it survives. scripts/mutate.py runs a list and checks the file is restored byte for byte; the list for the https work is kept in the repository (49 mutants: 47 killed, one the compiler refuses, one that survives because it is redundant by design). Mutation runs are by hand, not in CI.
  • Unit tests in lex-sys. lex-sys test runs tests/*_test.ls: 215 tests in 21 sets for the pure parts (the cron calendar, the delivery state, the idempotency index, the settings, the destination rules, DNS answers, the token bucket, the table of dead letters, the counters and the text of /metrics). lex-sys has no examples blocks, so each test is a function of assertions.
  • CI runs it all on every push and pull request: the formatting check, the authority pin, the unit tests, the 44 harness programs and shellcheck. It does not run the mutation lists or the benchmarks in scripts/bench/, which are reports.

Quick start

The same steps as the README. You build the pinned lex-sys compiler, then the service. It needs git, Rust, OpenSSL 3.0 or later with its development files (libssl-dev: the service is linked against it), and gcc for the small shims the tests preload.

git clone https://github.com/alpibrusl/lex-sys                          # the compiler, and nothing else to clone
git clone https://github.com/alpibrusl/lexsys-hooks && cd lexsys-hooks

REV=$(sed -n 's/^lex-sys *= *"\(.*\)"/\1/p' lex-sys.toml)                 # the compiler these sources were written for
(cd ../lex-sys && git fetch -q origin && git checkout "$REV" && cargo build --release -p lex-sys)
export LEX_SYS=$PWD/../lex-sys/target/release/lex-sys

scripts/build.sh                      # installs the libraries in lex-sys.toml, builds build/hooks (linked against OpenSSL) and the probes, and the shims the tests preload

# one endpoint: <id> <host> <port> <secret>
mkdir -p /tmp/hooks-data
echo "0 127.0.0.1 9000 whsec_$(python3 -c 'import os,base64;print(base64.b64encode(os.urandom(24)).decode())')" \
  > /tmp/hooks-data/endpoints.conf

build/hooks --port 8080 --dir /tmp/hooks-data --allow-private-hosts 1 &   # the receiver is on 127.0.0.1
curl -XPOST -d '{"type":"user.created","id":7}' localhost:8080/events      # {"id":1}, after the flush

With nothing listening on port 9000 the event is stored and retried (5 s, 5 min, ...). To watch a delivery arrive, run a receiver first. This one prints the three headers and the body of every delivery and answers 204:

import http.server

class H(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers["Content-Length"]))
        print(self.headers["webhook-id"], self.headers["webhook-timestamp"],
              self.headers["webhook-signature"], body.decode(), flush=True)
        self.send_response(204)
        self.send_header("Content-Length", "0")
        self.end_headers()

http.server.HTTPServer(("127.0.0.1", 9000), H).serve_forever()

A subscriber verifies a delivery with the reference library (pip install standardwebhooks). The key is the base64-decoded secret, which is what that library does:

Instead of building, every CI run that passes keeps the service as an artifact of the run: hooks-linux-x86_64-<commit>, for Linux x86-64 with the glibc of ubuntu-latest or newer. Artifacts expire (90 days by default) and no release with a stable URL is built.

With PostgreSQL

With --pg-host the endpoints come from the endpoints table, read once at start, and endpoints.conf is not read. The service does not wait for the database: it listens at once and takes events (202, stored in the log), but delivers nothing and answers 503 on the routes about endpoints until it has read the table, because a stale list would deliver to the wrong receivers. A login the database refuses for good, or a table that is missing, ends the start at once with status 20; a database that cannot be reached ends it with status 20 after pg-start-wait-ms (30 s). Once the table has been read the service never ends because of the database. The history is best effort: the service keeps delivering while the database is slow or gone, and counts the rows it could not write in /stats; a lost connection is remade by the service, with no restart.

createdb hooks && psql hooks -f sql/schema.sql
build/hooks --dir /var/lib/hooks --pg-host 127.0.0.1 --pg-user hooks_rw --import-endpoints 1   # copy endpoints.conf into the table, once
build/hooks --port 8080 --dir /var/lib/hooks --pg-host 127.0.0.1 --pg-user hooks_rw
psql hooks -c "select * from attempts where event = 41 order by endpoint, attempt"

Counters are since the start. Needs the read token when one is configured (the admin token does too); without one it is open, like the other reads.

Securing it

Out of the box the service is open: with no token configured anyone who can reach the port can post and read events. That suits a laptop. For anything else, give each scope a token and set production = 1, and the service will not start until nothing is left open.

# hooks.conf
port = 8080
dir = /var/lib/hooks
production = 1
admin-token  = <32 random characters>    # changes configuration or state; also does what the others do
ingest-token = <32 random characters>    # POST /events
read-token   = <32 random characters>    # the GETs (optional: without it the reads need the admin token)

curl -H "Authorization: Bearer $INGEST" -d '{"type":"user.created"}' localhost:8080/events
  • A request with no token or a wrong one is a 401 with WWW-Authenticate: Bearer. A valid token of a scope that does not reach the route is a 403 that names the token the route needs.
  • Tokens are 8 to 255 visible characters, compared in constant time, and appear in no answer, in /config or /stats, or on stderr. Keep them in the settings file, not on a command line. A change takes a restart.
  • production = 1 refuses to start, with an exit status and a line naming the setting or the path: 30 no admin-token; 31 no ingest-token; 32 allow-private-hosts is 1; 33 the data directory or one of its files can be read or written by its group or by others (make the directory 0700 and start with umask 077: the logs the service makes are 0666 less the umask); 34 two of the tokens are the same; 35 the mode of the directory cannot be read. A database is not required.
  • The database is the trust boundary for secrets. The endpoints’ signing secrets are stored in the clear in the endpoints table (the service signs with them), and there is no encryption at rest. Give the service’s database role only what it needs, keep the database off any network the receivers or senders share, and treat a backup like the secrets it holds.
  • Not built: TLS towards your own clients (put a reverse proxy in front), an audit log of who called what, a rate limit on failed tokens, token rotation without a restart.

What a receiver gets

POST /hook, event as the body, three headers: webhook-id (evt_<id>, the same on every attempt), webhook-timestamp (Unix seconds) and webhook-signature (v1, and the base64 HMAC-SHA256 of <id>.<timestamp>.<body> under the decoded secret; two, space separated, while a rotation overlaps), then the endpoint’s custom headers, if it has any. A 410 Gone makes the event a dead letter at once and disables the endpoint.

What it is not (yet)

The README says “Not for production”. The limits below are from docs/status.md, docs/production.md and the design document. What is left before that line is lifted, by the project’s own list: a soak test of at least 24 hours under chaos (kills, a dead endpoint, a slow database, with memory, descriptors and disk watched and its numbers published), a capacity page that gives the method behind the figures under “What it costs”, and the endpoint limit below. The soak test and the page are not built: no run of 24 hours has been made.

  • Open until you configure it. A scope with no token configured leaves its routes open, so a service started with only the defaults can be called by anyone who can reach the port. production = 1 refuses to start until the admin and ingest tokens are set. A token is the whole of the authentication: there is no audit log, no rate limit on failed tokens, and a token changes only with a restart. Whoever holds the admin token can choose where the service sends requests: by default the host must be a public IPv4 address, or a name that resolves only to public addresses (checked at every attempt, and the connection goes to the address that was checked), which keeps loopback, private, link-local (the cloud metadata address) and reserved ranges out of reach (§26, §40); there is no allow-list of particular hosts yet.
  • https costs a handshake a delivery. Delivery to an https:// endpoint verifies the certificate chain and the host name against the system’s trust store (or tls-ca-file), TLS 1.2 at least; every failure is a reason of its own. The service closes the connection after every delivery, so each costs a handshake (with ten endpoints, 1,033 µs of the service’s CPU a delivery with a full handshake and 683 µs resumed, against 100 µs plain: one core does about 970 and 1,460 a second, against 10,000; see “What it costs”). Revocation is not checked, there is no client certificate and no IPv6, and OpenSSL 3.0 or later is needed at run time (§40). The TLS is OpenSSL, in the process, until lex-sys’s own TLS can verify certificate chains and has been independently reviewed; a real public certificate chain was not exercised, only throwaway authorities.
  • Endpoints can be created, changed and deleted while it runs. They come from endpoints.conf, or from the endpoints table read at start, and POST /endpoints adds one. PATCH changes the host, port, secret, event types or headers (a new secret replaces the old at once unless a period to keep it is given: one signature, so a receiver that has not been given it refuses until it has). DELETE stops new attempts at once, lets one on the wire finish, and holds the slot until it has: with 62 endpoints a POST in that window is a 409 for up to the attempt’s deadline. There is no backfill: a created endpoint starts from now.
  • A row added by hand starts behind, not at the start. A row inserted into the table (or a line added to endpoints.conf) starts at the cursor of the slowest endpoint the log knows, so it cannot stall the others (it used to start at 0, and a receiver that was down held every endpoint to a window of 1,024 events; §25.3. Each endpoint has its own window now, §31, and the rule stays as a policy). It is sent that endpoint's backlog; POST /endpoints starts from now.
  • Cron is bounded. UTC only; at most 64 schedules; one service per database (a second would fire the same rows into its own log). Every fire uses an idempotency key; the index forgets a key when its window has passed or its event is dropped by retention, so a schedule of every minute no longer fills it (it did in 45 days before §38), and a fire that finds the index full is still refused and counted in cron_errors, not made without its key (§32.7). A jump of the machine’s clock is a stop or a restart as far as a schedule can tell.
  • Secrets and header values are stored in the clear in the file or table, the previous secret of a rotation too: the database is the trust boundary (see “Securing it”), and the table has the permissions of a secret. The endpoints table is read at start as one text of at most 32 KiB, which large header sets on many endpoints can fill.
  • One process, one thread, one core. Up to 64 attempts are in flight, 8 per endpoint, and at most 62 endpoints. An endpoint is served at most 1,024 events past its own cursor; the rest of its events wait in the log, and that does not hold up another endpoint (§31). A dead endpoint dead-letters its events at the speed of the retry schedule until the circuit breaker pauses it, which takes a failed attempt more than breaker-days (5) days after its run of failures began, and nothing resumes it but a person (POST /endpoints/:id/enable).
  • Names are resolved by the service, over TCP, to one name server. A host name is looked up at every attempt without holding the loop, and the connection goes to the address that was checked (a name that resolves to a private address is a failed attempt, ssrf_refused); there is no /etc/hosts (except localhost), no search list, no UDP, no second server and no IPv6 (§40).
  • No strict ordering. After a failure, the retry of event N and the first attempt of event N+1 are not ordered. After a crash an event can be delivered twice, which is why webhook-id is stable.
  • The database. A host name for pg-host stalls the loop while it resolves: give an address. The endpoints table is read once, so a row changed behind the service’s back, or a change whose outcome it did not learn (a 504), is seen at the next start. The attempts table is not pruned.
  • The history is best effort. It can have holes. While the database is away the rows wait in a queue of 256 and the rest are dropped and counted; the service reconnects by itself, and it does not wait for the database at start (it takes events and delivers once it has read its endpoints).
  • A stop is bounded, and the socket stays open. A drain waits at most stop-deadline-ms; what is still on the wire is made again at the next start. The listening socket stays open until the process exits, and a connection that arrives meanwhile is answered 503 and closed.
  • Bounded by design. Events over about 64 KiB are refused (413; 65,499 bytes less 11 and the length of the stored type). At most idem-keys (262,144 by default) idempotency keys that are still fresh; a key is forgotten after window-ms or when its event is dropped. The logs are bounded by retention and not by history (§38): an event is deleted, a segment at a time, only when it is delivered or dead-lettered at every endpoint and older than retention-days (30 by default; 0 keeps them for ever), after which GET /events/:id and its replay are 404 and the same Idempotency-Key posted again is a new event; delivery.seg is replaced by a snapshot of the state it replays to, and the largest possible snapshot (62 endpoints with full windows, 4.9 MB) holds the loop for 40 to 70 ms (measured; a typical one, a few milliseconds).
  • Limits are held in memory. A restart starts every rate bucket full, so a rate limit can be exceeded by a tenth of a second’s worth across a restart. The dead letters of an endpoint are listed from a table of its newest 2,048; older ones are completed from the log when there is room, until a snapshot of the log keeps the table and not what it left out. A dead letter leaves the list when retention deletes its event.
  • Wide authority where it must be. The data directory is a run-time argument and deliveries may go to any public address, so the authority report is not narrowed to a path or a host; and the foreign calls (one into libc, 32 into OpenSSL) make the report open with UNBOUNDED: the program calls foreign code, and the labels do not bound what it can reach. CI pins the exact list of symbols (scripts/check-authority.sh), so a new one is a red diff until a person commits it.
  • Binaries and packaging. Only the CI artifact, for Linux x86-64; macOS is not verified. The Dockerfile was built and run by hand and is not built in CI, the systemd unit was checked with systemd-analyze and never run under a real systemd, and the release script does not sign, has no stable URL and writes a stub where an SBOM would be.
