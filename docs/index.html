lexsys-hooks

A webhook delivery service, written in lex-sys. You POST it an event; it stores the event durably and delivers it, signed, to every configured endpoint, at least once, retrying on a schedule and keeping what it could not deliver as a dead letter.

It is also a realistic program that exercises the lex-sys stack, so that what is missing shows up as a failing test rather than a guess. The repository’s design document records what each step built and measured, including what failed.

What it does today

Durable ingest

An accepted event is appended to a lexsys-log segment and answered 202 only after the flush. Requests that arrive together share one flush (group commit).

Signed delivery

Each delivery is a POST /hook with webhook-id, webhook-timestamp and webhook-signature (HMAC-SHA256, v1, and base64). Any 2xx is a delivery.

Retries and dead letters

Failures retry on the Standard Webhooks schedule; after the last retry the event is a dead letter for that endpoint. Every outcome, with the time of the next attempt, survives a crash.

Idempotency keys

Send the same Idempotency-Key with the same event and you get the first answer back, byte for byte, and nothing more is stored, also across a crash.

Replay, and 410 Gone

POST /events/:id/replay sends an event again to one endpoint or all, with the same webhook-id. A 410 Gone dead-letters the event and disables the endpoint until you enable it.

A slow endpoint does not hold up the rest, for a while

Delivery attempts do not hold the loop: up to 64 are in flight, 8 per endpoint, so a slow, silent or unreachable endpoint costs the others almost nothing until it is 1,024 events behind; then all endpoints stop with it (measured: a healthy endpoint stopped at 1,024 of 3,000 events beside a dead one; §29). Fixing that is the first item of the production plan.

PostgreSQL, optionally

With --pg-host, endpoints are the rows of an endpoints table and every ended attempt is a row of attempts, read back at GET /events/:id/attempts. With an admin-token an endpoint can be created while the service runs.

Small authority

No Ffi, no unsafe. The service releases its Ffi capability at start and the compiler’s authority report names what it can do.

How it works in one minute

One thread, one poller. Ingest and delivery run in the same loop.

  1. Ingest. POST /events takes a JSON object with a string "type". The event is appended to the events log and its request is held.
  2. One flush per turn. After the turn of the loop, a single flush covers every append. Only then are the held requests answered 202 {"id":N}.
  3. Attempts that do not block. Each delivery attempt is a small state machine (connecting, sending, reading) watched on the server’s own poller. Each endpoint has a cursor, and a window of events above it, so a failing event does not hold up the ones after it.
  4. The request. POST /hook to the endpoint, event as the body, signed with the endpoint’s secret.
  5. The outcome. Delivered, failed (with the Unix time of the next attempt) or dead is appended to a second log, delivery.seg, with one flush per turn. A restart replays it, so counts and delays survive.
  6. Optional history. With a database, each ended attempt is also a row in PostgreSQL. The log files stay the truth about delivery; the history is best effort.

The retry schedule

Each delay counts from the previous attempt. A 2xx is a delivery; anything else, a timeout or a refused connection is a failure. These are the defaults, and the schedule setting changes them. No jitter is built yet.

Quick start

The same steps as the README. You build the pinned lex-sys compiler, then the service. It needs git, Rust, and gcc for the small fsync shim the crash tests use.

git clone https://github.com/alpibrusl/lex-sys                          # the compiler, and nothing else to clone
git clone https://github.com/alpibrusl/lexsys-hooks && cd lexsys-hooks

REV=$(sed -n 's/^lex-sys *= *"\(.*\)"/\1/p' lex-sys.toml)                 # the compiler these sources were written for
(cd ../lex-sys && git fetch -q origin && git checkout "$REV" && cargo build --release -p lex-sys)
export LEX_SYS=$PWD/../lex-sys/target/release/lex-sys

lex-sys build                         # installs the two libraries in lex-sys.toml, then builds build/hooks and build/sign_probe
scripts/build.sh                      # the same, and the fsync shim the crash tests preload

# one endpoint: <id> <host> <port> <secret>
mkdir -p /tmp/hooks-data
echo "0 127.0.0.1 9000 whsec_$(python3 -c 'import os,base64;print(base64.b64encode(os.urandom(24)).decode())')" \
  > /tmp/hooks-data/endpoints.conf

build/hooks --port 8080 --dir /tmp/hooks-data --allow-private-hosts 1 &   # the receiver is on 127.0.0.1
curl -XPOST -d '{"type":"user.created","id":7}' localhost:8080/events      # {"id":1}, after the flush

With nothing listening on port 9000 the event is stored and retried (5 s, 5 min, ...). To watch a delivery arrive, run a receiver first. This one prints the three headers and the body of every delivery and answers 204:

import http.server

class H(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers["Content-Length"]))
        print(self.headers["webhook-id"], self.headers["webhook-timestamp"],
              self.headers["webhook-signature"], body.decode(), flush=True)
        self.send_response(204)
        self.send_header("Content-Length", "0")
        self.end_headers()

http.server.HTTPServer(("127.0.0.1", 9000), H).serve_forever()
$ python3 receiver.py &

A subscriber verifies a delivery with the reference library (pip install standardwebhooks). The key is the base64-decoded secret, which is what that library does:

from standardwebhooks import Webhook
Webhook("whsec_...").verify(body, {"webhook-id": "evt_1", "webhook-timestamp": "1791028548",
                                   "webhook-signature": "v1,5Zm7..."})   # raises if the signature or timestamp is wrong

Instead of building, every CI run that passes keeps the service as an artifact of the run: hooks-linux-x86_64-<commit>, for Linux x86-64 with the glibc of ubuntu-latest or newer. Artifacts expire (90 days by default) and no release with a stable URL is built.

Settings

From a file (--config), from flags, or both; the last source that names a setting wins. --port and --dir are required. Anything unknown is refused before the service listens, with exit code 2. GET /config says what is in force.

With PostgreSQL

With --pg-host the endpoints come from the endpoints table, read once at start, and endpoints.conf is not read. A database that cannot be read is a refusal to start, because a stale list would deliver to the wrong receivers. The history is best effort: the service keeps delivering while the database is slow or gone, and counts the rows it could not write in /stats.

createdb hooks && psql hooks -f sql/schema.sql
build/hooks --dir /var/lib/hooks --pg-host 127.0.0.1 --pg-user hooks_rw --import-endpoints 1   # copy endpoints.conf into the table, once
build/hooks --port 8080 --dir /var/lib/hooks --pg-host 127.0.0.1 --pg-user hooks_rw
psql hooks -c "select * from attempts where event = 41 order by endpoint, attempt"

HTTP API today

These are the routes the service registers now. Only POST /endpoints is behind a token; none of the others is authenticated.

RouteWhat it does
POST /eventsA JSON object with a string "type", and optionally an Idempotency-Key (1 to 255 visible ASCII characters). 202 {"id":N} after the flush; 422 for a body that is not an event, or a key already used for a different event; 400 for a bad or doubled key; 413 for an event too large; 507 for a new key when 65,536 are held; 503 if the log is broken.
GET /events/:idThe stored event, or 404.
POST /events/:id/replay
POST /events/:id/replay/:endpoint		Send the event again to every endpoint, or to one. 202 with the event and endpoints; 404 for an unknown event or endpoint; 507 if 32 replays already wait. Same webhook-id, same schedule.
GET /events/:id/attemptsThe attempts of an event, from the database: endpoint, replay, attempt, outcome, status, time, latency. 503 if no database is named or it cannot answer, 504 after five seconds.
GET /endpointsEach endpoint’s id, port, cursor and whether it is disabled. Not the host, not the secret.
GET /endpoints/:idOne endpoint, as the list shows it. 404 for an unknown id, 400 for one that is not a number.
POST /endpointsCreate an endpoint: {"host","port"} and optionally "secret" (whsec_ and base64; the service makes one if it is left out). Needs a database and an admin-token and Authorization: Bearer <token>. 201 with the id, host, port and the secret, in this answer and no other; the endpoint gets events from now on, not the log’s past. 403 if the service has no token, 401 without the right one, 400 with a reason, 409 if another change is waiting or 62 exist, 503 if no database is named or it refused, 504 after five seconds.
PATCH /endpoints/:idChange an endpoint (admin token, and a database): any of "host", "port", "secret" and "rotate": true. 200 with the new address, and the secret once if the change brought or made one. The next attempt uses it; an attempt already on the wire finishes against the old address. 404 unknown id or row gone, 409 while another change waits, 400 with a reason, 503 if the database refuses.
DELETE /endpoints/:idRemove an endpoint (admin token, and a database). The row goes first; when the database says commit, no new attempt starts for the endpoint and it leaves GET /endpoints at once. An attempt already on the wire finishes and is recorded under the endpoint’s id, and its slot is not reused until it has; replays waiting for it are dropped; its history rows are kept and its id is never given again. 200 with deleted and draining (a row that was already gone is removed from the service all the same); 404 unknown id, 400 not a number, 409 while another change waits or every slot is taken, 503 if the database refuses (nothing changes), 504 after five seconds.
POST /endpoints/:id/enableEnable an endpoint a 410 disabled. 200 whether or not it was disabled; 404 for an unknown id.
GET /statsCounters: endpoints, attempts, delivered, failed, dead, keys, replays, draining (deleted endpoints with an attempt still on the wire), and four for the history.
GET /configThe settings in force, not the endpoints or their secrets.
GET /healthz{"ok":true}

What a receiver gets

POST /hook, event as the body, three headers: webhook-id (evt_<id>, the same on every attempt), webhook-timestamp (Unix seconds) and webhook-signature (v1, and the base64 HMAC-SHA256 of <id>.<timestamp>.<body> under the decoded secret). A 410 Gone makes the event a dead letter at once and disables the endpoint.

What it is not (yet)

The README says “Not for production”. The limits below are from the README and the design document.

  • Almost no authentication. POST /endpoints needs the admin token, and the token is the only barrier: an endpoint is an address the service will POST to, so whoever holds it can choose where the service sends requests. By default the host must be a public IPv4 address, which keeps loopback, private, link-local (the cloud metadata address) and reserved ranges out of reach (§26); there is no allow-list of particular hosts yet. Every other route, including POST /events and POST /endpoints/:id/enable, can be called by anyone who can reach the port.
  • No TLS. Delivery is a plain-HTTP POST /hook to a host and port; https endpoints are not supported.
  • Endpoints can be created, changed and deleted while it runs. They come from endpoints.conf, or from the endpoints table read at start, and POST /endpoints adds one. PATCH changes the host, port or secret (a new secret replaces the old at once: one signature, so a receiver that has not been given it refuses until it has). DELETE stops new attempts at once, lets one on the wire finish, and holds the slot until it has: with 62 endpoints a POST in that window is a 409 for up to the attempt’s deadline. There is no backfill: a created endpoint starts from now.
  • A row added by hand starts behind, not at the start. A row inserted into the table (or a line added to endpoints.conf) starts at the cursor of the slowest endpoint the log knows, so it cannot stall the others (it used to start at 0, and a receiver that was down held every endpoint to a window of 1,024 events; §25.3). It is sent that endpoint's backlog; POST /endpoints starts from now.
  • No filtering by event type. Every event goes to every endpoint. Secrets are stored in the clear in the file or table.
  • One process, one thread, one core. Up to 64 attempts are in flight, 8 per endpoint, and at most 62 endpoints. One endpoint that is more than 1,024 events behind stops every endpoint, not only itself: the scan of the events log is bounded by the slowest cursor (measured; §29).
  • Use IP addresses. A host name is resolved by a blocking call that stalls the loop for as long as the resolver takes.
  • No strict ordering. After a failure, the retry of event N and the first attempt of event N+1 are not ordered. After a crash an event can be delivered twice, which is why webhook-id is stable.
  • The history is best effort. It can have holes. A lost database connection is not reopened until the service restarts, and the start waits while the database is silent.
  • Bounded by design. Events over about 64 KiB are refused (413). At most 65,536 idempotency keys, and the index does not shrink. delivery.seg and the events log are never compacted. There is no list of dead letters and no way to cancel a waiting replay.
  • No jitter in the retry schedule, and no secret rotation with two signatures.
  • Wide authority where it must be. The data directory is a run-time argument and deliveries may go to any public address, so the authority report is not narrowed to a path or a host. No CI step pins the report today (it is planned in §6).
  • Binaries. Only the CI artifact, for Linux x86-64. Darwin is not verified.
