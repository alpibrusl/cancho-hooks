Examples

Seven situations, each a script you can run. What you read is what the script printed, and CI checks that it still is. Each card also has a recording of the run: play it here, or with asciinema play examples/casts/02-payments.cast. The waits in a recording are shortened to 1.5 seconds, so a script that waited longer plays faster than it ran.

You need the built service, bash, curl and python3; examples 1 and 4 also need a PostgreSQL they may empty. Each script starts its own service on a free port and stops it. receiver.py is the receiver: it verifies every signature. Start with the README.

1Send your customers webhooks

Each customer gets an endpoint of its own: its own secret, filter, header and limits. An event reaches only the endpoints that subscribe, every delivery is signed, and a secret can be rotated while the customer's receiver goes on verifying.

# two customers: acme wants invoices, at most 2 requests at once and 10 a second; globex wants everything
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/endpoints -H "Authorization: Bearer $ADMIN" -d '{"host":"127.0.0.1","port":'$ACME_PORT',"types":["invoice.*"],"headers":{"X-Customer":"acme"},"concurrency":2,"rate":10}'
{"id":0,"host":"127.0.0.1","scheme":"http","port":…,"secret":"whsec_…","from":"now","cursor":0} [201]
# each secret is in the answer that made the endpoint and in no other; it goes to the customer, who keeps it
$ curl -s $URL/endpoints -H "Authorization: Bearer $ADMIN"
[{"id":0,"port":…,"types":["invoice.*"],"headers":["X-Customer"],…"concurrency":2,"rate":10},{"id":1,…"types":[],…
# an invoice goes to both; a new user goes to globex only
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d '{"type":"invoice.paid","invoice":"INV-1001","amount":4900}'
{"id":1} [202]
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d '{"type":"user.created","user":"u_77"}'
{"id":2} [202]
acme evt_1 signature ok (1 signature) {"type":"invoice.paid","invoice":"INV-1001","amount":4900} X-Customer=acme
globex evt_1 signature ok (1 signature) {"type":"invoice.paid","invoice":"INV-1001","amount":4900} X-Customer=globex
globex evt_2 signature ok (1 signature) {"type":"user.created","user":"u_77"} X-Customer=globex
$ curl -s $URL/stats -H "Authorization: Bearer $ADMIN" | grep -oE '"(delivered|failed|filtered)":[0-9]+'
"delivered":3
"failed":0
"filtered":1
# acme rotates its secret: deliveries are signed with the new one and, for a day (keep_old), with the old one too
$ curl -s -w ' [%{http_code}]\n' -X PATCH $URL/endpoints/$ACME_ID -H "Authorization: Bearer $ADMIN" -d '{"rotate":true,"keep_old":true}'
{"id":0,…"secret":"whsec_…","secret_old_until":…} [200]
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d '{"type":"invoice.paid","invoice":"INV-1002","amount":1500}'
{"id":3} [202]
acme evt_3 signature ok (2 signatures) {"type":"invoice.paid","invoice":"INV-1002","amount":1500} X-Customer=acme
# acme switches its receiver to the new secret, at its own time
$ echo "$ACME_NEW" > acme.secret
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d '{"type":"invoice.paid","invoice":"INV-1003","amount":700}'
{"id":4} [202]
acme evt_4 signature ok (2 signatures) {"type":"invoice.paid","invoice":"INV-1003","amount":700} X-Customer=acme
# when acme is ready it ends the overlap, and only the new signature is sent
$ curl -s -w ' [%{http_code}]\n' -X PATCH $URL/endpoints/$ACME_ID -H "Authorization: Bearer $ADMIN" -d '{"keep_old_ms":0}'
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d '{"type":"invoice.paid","invoice":"INV-1004","amount":300}'
acme evt_5 signature ok (1 signature) {"type":"invoice.paid","invoice":"INV-1004","amount":300} X-Customer=acme
$ curl -s $URL/stats -H "Authorization: Bearer $ADMIN" | grep -oE '"(delivered|failed)":[0-9]+'
"delivered":9
"failed":0
ok: no delivery failed, rotation included

Limits. Delivery is at least once: a receiver can be sent an event again and the webhook-id is then the same. Creating endpoints while the service runs needs PostgreSQL and an admin token. The limits (concurrency 2, rate 10) are shown in the list; example 5 shows concurrency at work.

2Payments that must not be lost or doubled

The 202 comes after the event is on disk. A client that asks twice with the same Idempotency-Key gets the same id, not a second event. Kill the service hard and the event is still delivered when it is back, with the same webhook-id every time it is sent.

$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -H 'Idempotency-Key: order-1042' -d '{"type":"payment.captured","order":1042,"amount":4900}'
{"id":1} [202]
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -H 'Idempotency-Key: order-1042' -d '{"type":"payment.captured","order":1042,"amount":4900}'
{"id":1} [202]
ok: the same id comes back: one event
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -H 'Idempotency-Key: order-1042' -d '{"type":"payment.captured","order":1042,"amount":9900}'
{"error":"this Idempotency-Key was used for a different event"} [422]
# the 202 came after the event was flushed to disk. Now the service dies, hard, before it has delivered anything
$ kill -9 $SVC_PID
$ hooks --config hooks.conf --port $PORT --dir $DATA --schedule 500,500,500,500,500,500 --retry-jitter 0 &
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -H 'Idempotency-Key: order-1042' -d '{"type":"payment.captured","order":1042,"amount":4900}'
{"id":1} [202]
ok: still the same id
# the shop's server comes back
$ python3 examples/receiver.py --name shop --port $SHOP_PORT --secret-file shop.secret &
shop evt_1 signature ok (1 signature) {"type":"payment.captured","order":1042,"amount":4900}
ok: it arrived, once, although the service was killed and the shop was down
# a repeat of a delivery has the same webhook-id (evt_1): the receiver drops it. Here the service is asked to send the event again
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events/1/replay -H "Authorization: Bearer $ADMIN"
{"event":1,"endpoints":[0]} [202]
shop evt_1 signature ok (1 signature) duplicate

Download the recording (.cast)

Limits. Delivery is at least once, not exactly once: a repeat is possible, and the receiver drops it by webhook-id, as the one here does. The demo shortens the retry delays; the default first retry is 5 seconds.

Run it: examples/02-payments.sh · the script · Docs: POST /events · Idempotency, how it works · What is tested

3A customer's endpoint is down

The service retries on a schedule. When it runs out, the event is a dead letter of that endpoint: kept, listed, and sent again in bulk when the customer is back.

$ hooks --config hooks.conf --port $PORT --dir $DATA --schedule 200,300,400 --retry-jitter 0 &
$ for i in 1 2 3; do curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d "{\"type\":\"order.shipped\",\"order\":$i}"; done
{"id":1} [202]
{"id":2} [202]
{"id":3} [202]
$ curl -s "$URL/endpoints/0/dead?limit=2"
{"endpoint":0,"order":"desc","held":3,…"dead":[{"event":3,"type":"order.shipped","attempts":4,"reason":"connect_refused",…
# the customer is back
$ python3 examples/receiver.py --name customer --port $CUSTOMER_PORT --secret-file customer.secret &
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/endpoints/0/replay-dead -H "Authorization: Bearer $ADMIN"
{"endpoint":0,"taken":3,"remaining":0,"waiting":3,"next":3} [202]
customer evt_1 signature ok (1 signature) {"type":"order.shipped","order":1}
customer evt_2 signature ok (1 signature) {"type":"order.shipped","order":2}
customer evt_3 signature ok (1 signature) {"type":"order.shipped","order":3}
$ curl -s "$URL/endpoints/0/dead"
{"endpoint":0,"order":"desc","held":0,…"dead":[],"next":null}

Download the recording (.cast)

Limits. The demo uses --schedule 200,300,400 (four attempts in about a second). The default is nine retries over about three days: 5 s, 5 min, 30 min, 2 h, and so on up to 24 h between the last two attempts. An endpoint lists at most 2,048 dead letters; an older one is replayed by its event id.

Run it: examples/03-endpoint-down.sh · the script · Docs: Retries, dead letters, bulk replay · The routes

4A report every Monday, with no scheduler

A schedule is a cron expression in UTC. The service makes an ordinary event on it, so a fire is signed, retried and replayable like any other.

$ curl -s -w ' [%{http_code}]\n' -X POST $URL/schedules -H "Authorization: Bearer $ADMIN" -d '{"expr":"0 6 * * 1","type":"report.due","body":{"report":"weekly"}}'
{"id":1,"expr":"0 6 * * 1",…"next_fire_at":"…"} [201]
ok: the next fire is a Monday, 06:00:00 UTC
# part two: the same, with seconds, so that it can be watched (a fire every 2 seconds)
$ hooks --config hooks.conf --port $PORT --dir $DATA --cron-seconds 1 &
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/schedules -H "Authorization: Bearer $ADMIN" -d '{"expr":"*/2 * * * * *","type":"report.due","body":{"report":"weekly"}}'
# nothing else sends events: these are the fires
reports evt_1 signature ok (1 signature) {"type":"report.due","schedule":2,"scheduled_at":…,"body":{"report":"weekly"}}
reports evt_2 signature ok (1 signature) {"type":"report.due","schedule":2,"scheduled_at":…,"body":{"report":"weekly"}}
$ curl -s $URL/stats | grep -o '"cron_fired":[0-9]*'
ok: the fires the service counted are the verified deliveries the receiver has: none lost, none doubled
# a fire is an event like any other: it can be sent again, with the same webhook-id
$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events/1/replay -H "Authorization: Bearer $ADMIN"
{"event":1,"endpoints":[0]} [202]
reports evt_1 signature ok (1 signature) duplicate

Download the recording (.cast)

Limits. Five fields, numbers only, UTC. The second half runs the service with --cron-seconds 1, a mode for demos and tests that adds a seconds field, so that a fire can be watched in seconds instead of on Monday. One service per database: a second one reading the same schedules would fire them too. Needs PostgreSQL and an admin token.

Run it: examples/04-cron.sh · the script · Docs: Schedules · The routes

5One event, several internal systems

Three systems read the same stream, each with the types it needs and a pace of its own. A slow one waits its turn and does not hold up the others.

$ cat > $DATA/endpoints.conf <<EOF
0 127.0.0.1 $BILLING_PORT $(cat billing.secret) types=invoice.*
1 127.0.0.1 $AUDIT_PORT $(cat audit.secret)
2 127.0.0.1 $SEARCH_PORT $(cat search.secret) types=invoice.*,user.* concurrency=1
EOF
$ python3 examples/receiver.py --name search --port $SEARCH_PORT --secret-file search.secret --delay 1.5 &
$ for t in invoice.paid user.created invoice.refunded invoice.paid; do curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d "{\"type\":\"$t\"}"; done
# what each receiver got, and when it had it all (from the first event posted)
billing: 3 deliveries (invoice.*), done after … ms
audit:   4 deliveries (everything), done after … ms
search:  4 deliveries (invoice.*, user.*; 1.5 s each, one at a time), done after … ms
ok: the two fast receivers were done in less than half the time the slow one needed

Download the recording (.cast)

Limits. One process, up to 64 attempts in flight together. The times above are from one machine and one run: the script only requires that the fast ones finish in under half the slow one's time.

Run it: examples/05-several-systems.sh · the script · Docs: Pace: concurrency and rate · endpoints.conf · Capacity

6Erase and expire personal data

Erase one event on request: its body leaves the files, the endpoint never gets it and reading it answers 410. Or set a maximum age, which drops events that an endpoint that is down would otherwise keep for ever.

$ curl -s -w ' [%{http_code}]\n' -X POST $URL/events -d '{"type":"customer.updated","email":"ana@example.com"}'
{"id":1} [202]
$ grep -rl ana@example.com $DATA | sed "s|^$DATA/||"
events.seg
$ curl -s -w ' [%{http_code}]\n' -X DELETE $URL/events/1 -H "Authorization: Bearer $ADMIN"
{"id":1,"erased":true} [200]
$ curl -s -w ' [%{http_code}]\n' $URL/events/1
{"error":"the event was erased (DELETE /events/:id)"} [410]
$ (grep -rl ana@example.com $DATA || echo 'ana@example.com: in no file') | sed "s|^$DATA/||"
ana@example.com: in no file
# what is not erased: the event's type (and its id, its size and its idempotency key if it had one)
$ grep -rao customer.updated $DATA | sed "s|^$DATA/||"
events.seg:customer.updated
# the customer's server comes back: it gets the event that is left, and never the erased one
customer evt_2 signature ok (1 signature) {"type":"order.created","email":"ben@example.com"}
ok: only the event that was not erased arrived
# part two. Events that nothing may keep: an endpoint that is down pins them (retention only drops what is final everywhere)
$ curl -s -o /dev/null -w '%{http_code}\n' $URL/events/1
200
# the same data, with a maximum age of 3 seconds (the real setting is --max-age-days; this is its knob for tests)
$ hooks --config hooks.conf --port $PORT --dir $DATA --segment-bytes 262144 --schedule 3600000 --max-age-ms 3000 &
$ curl -s -o /dev/null -w '%{http_code}\n' $URL/events/1
410
$ curl -s $URL/stats | grep -oE '"(events_expired|segments_expired)":[0-9]+'
"events_expired":…
"segments_expired":…
ok: the expired events are counted, not hidden

Download the recording (.cast)

Limits. Not erased: the event's type, id, size and idempotency key; the history rows (they hold no body); backups taken before the erasure; and the copies the receivers already have. The service does not index bodies by person, so an access request needs the event ids. Not legal advice; the page says what the service does.

Run it: examples/06-erase-and-expire.sh · the script · Docs: Privacy and audit: what is held, what is erased, what is not · Retention and the maximum age

7Let an agent look

hooks-mcp lets an AI agent read events, dead letters and attempts over MCP. Without --allow-write the tools that change anything are not even offered.

$ hooks-mcp --url $URL < requests.jsonl > replies.jsonl; echo "$(wc -l < replies.jsonl) replies"
5 replies
$ grep '"id":2,' replies.jsonl | grep -o '"name":"hooks_[a-z_]*"'
"name":"hooks_health"
"name":"hooks_stats"
"name":"hooks_get_event"
"name":"hooks_list_endpoints"
"name":"hooks_list_dead_letters"
"name":"hooks_get_attempts"
$ grep -E '"id":[345],' replies.jsonl
{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"{\"id\":1,\"event\":{\"type\":\"order.shipped\",\"order\":7}}"}],"isError":false}}
{"jsonrpc":"2.0","id":4,"result":{"content":[{"type":"text","text":"{\"endpoint\":0,…
{"jsonrpc":"2.0","id":5,"error":{"code":-32602,"message":"Invalid params: unknown tool"}}
$ curl -s -w ' [%{http_code}]\n' $URL/events/2
{"error":"no such event"} [404]

Download the recording (.cast)

Limits. An event's body goes to the agent's model: decide that before giving it the tool. It speaks plain HTTP to a service on this machine, or through a tunnel; it is not given secrets, endpoint changes or erasure.
