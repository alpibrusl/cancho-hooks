The proof, from the compiler

cancho’s compiler writes down what a program may do: not what its documentation promises, but what its instructions can reach. Every cancho-hooks build has that report committed and CI-checked, so a new capability or a new foreign call is a diff a person must approve. This page shows all four reports, every label explained — and where the honest answer is not bounded, it says so.

Four different jobs

Read them as the claim: the word “proof” on this page covers the first, and the reports below are that first job’s output.

The compilerproves the capability boundary of each build: which effects its instructions can reach. Derived, recorded, CI-checked.
The serviceenforces the delivery policy inside that boundary: destinations are public addresses only, scoped tokens, graceful stop.
The testschallenge the enforcement: kills, database cuts, receivers that hang, reset and lie — with a separate checker for loss, repetition and bad signatures (the evidence).
CIkeeps the evidence aligned with the source: the reports are re-derived on every push, and a drift is a red build.

A change to any of the four reports fails CI before it fails a reader (scripts/check-authority.sh, its --pure, --mcp and --logcheck variants). The approval of a new capability is the commit of its report.

Check it yourself

The reports are plain JSON in the repository, and the tool that compares them to what the compiler derives is one script.

git clone https://github.com/alpibrusl/cancho-hooks && cd cancho-hooks
scripts/build.sh                                  # builds build/hooks
scripts/check-authority.sh                        # red if docs/authority.json is not what the compiler derives
scripts/check-authority.sh --pure                 # the same for hooks-pure (cancho's own TLS)
cat docs/authority.json | python3 -m json.tool | head -20

Run 3 of the 24-hour chaos soak ended inconclusive at 15.8 hours (the harness ran out of capacity, not the service as far as is known) — the soak notes say exactly what that means, and the capacity figures a valid run would give are not published.

What this does not prove

  • A capability boundary is not a security review. The reports say what the builds can reach; they do not certify that the logic inside those bounds is free of bugs. The chaos tests are the other half of the story, and they are not a substitute for an external audit. Alpha: not for production.
  • The default build is not bounded, on purpose and by name. Its report lists all 32 OpenSSL symbols it can call (unbounded_by), which is why bounded is false for it. hooks-pure is the bounded build — and cancho’s own TLS it uses is not yet independently reviewed.
  • Delivery destinations are enforced, not proved. The network bound is not narrowed: net_out(""). Deliveries go only to public addresses by code and by test, not by compiler proof.
  • PostgreSQL, when you use it, is outside the report: it is another process the service talks to over a connection, like any endpoint.

Why this exists

cancho is a typed systems language whose compiler writes down what a program may do. A webhook service holds your events and sends them in your name: for code in that position, “the report says what it can reach” is the sentence that scales with distrust.
